# 端到端场景评测设计

> **目标**: 将现有的 45 场景定性评测升级为可量化的、可复现的回归测试体系
> **核心问题**: 53% 通过率不能写进简历。先修 P0 bug，再重测，再用数字说话
> **预计产出**: 5 维度量化评分、通过率 ≥ 75%、回归测试脚本化

---

## 一、现状分析

### 1.1 当前评测（`test_api_v3.sh`）的问题

2026-07-28 的 45 场景评测是一次**定性的人工审查**——你手动看每条回复，判断 pass/⚠️/fail。这是很好的产品反馈，但不是简历材料，因为：

1. **53% 通过率太低** — 不能写进简历
2. **评分标准不透明** — pass/⚠️/fail 的边界依赖你的直觉，无法被第三方复现
3. **脚本不可复现** — `test_api_v3.sh` 调用 HTTP API，依赖真实 LLM（DeepSeek）和真实 Bangumi API。一个月后重跑可能得到不同结果（模型更新、API 数据变化）
4. **没有评分量表** — "人格差异肉眼可辨" 不能变成数字

### 1.2 45 场景的复查

| 维度 | 场景数 | 通过 | ⚠️ | ❌ | 通过率 | 主要问题 |
|------|--------|------|-----|-----|--------|---------|
| A. 输出质量 | 8 | 4 | 2 | 2 | 50% | 字数超标、常识误触发工具 |
| B. 人格对比 | 16 | 15 | 1 | 0 | **94%** ✅ | cute 推荐与 neutral 重叠 |
| C. 工具策略 | 7 | 2 | 1 | 4 | **29%** | 迭代过多、字数、凭印象矛盾 |
| D. 真实场景 | 8 | 4 | 3 | 1 | 50% | 长程失忆、bare title |
| E. 边界压力 | 10 | 3 | 3 | 4 | 30% | E8 8轮失忆、deep 不调工具 |
| **总计** | **45** | **24** | **9** | **12** | **53%** | |

### 1.3 P0 问题修复预期

修复 4 个 P0 问题后（字数控制硬截断、deep 模式工具调用保证、常识→realtime 误分类、搜索空结果 2 轮放弃），预期变化：

| 维度 | 当前通过率 | 修复后预期 | 影响场景 |
|------|-----------|-----------|---------|
| A. 输出质量 | 50% | ~75% | A4(常识), A6(字数) |
| C. 工具策略 | 29% | ~71% | C3(凭印象), C4(字数), C7(空搜索) |
| D. 真实场景 | 50% | ~63% | D4(字数), D5(deep 工具), D7(字数) |
| E. 边界压力 | 30% | ~60% | E5(字数), E6(deep 工具), E8(需要 L1 增强) |
| **总计** | **53%** | **~70-75%** | |

E8（8 轮回溯失忆）可能需要 L1 预算/压缩策略调整，不一定能在 P0 修复中解决。

## 二、评测升级方案

### 2.1 从 pass/fail 到 5 分制评分量表

为每个维度定义明确的分级标准，让评分可复现：

#### A. 输出质量（8 场景）

| 分数 | 标准 |
|------|------|
| 5 | 回复满足用户意图，字数在限制 × 1.2 内，无格式问题，工具使用恰当 |
| 4 | 回复满足意图，但字数略超标（≤ 1.5×），或有一处小瑕疵 |
| 3 | 回复勉强满足意图，但字数明显超标，或信息不完整 |
| 2 | 回复部分偏离意图，或关键信息错误 |
| 1 | 回复完全偏离意图，或工具调用灾难性错误 |

#### B. 人格对比（16 场景）

| 分数 | 标准 |
|------|------|
| 5 | 四种人格回复在语气、态度、措辞上有明显且一致的差异；LLM judge 分类准确率 100% |
| 4 | 有明显差异但两种人格在个别探针上接近；分类准确率 ≥ 75% |
| 3 | 存在差异但不够锐利；分类准确率 ≥ 50% |
| 2 | 两种以上人格回复高度相似；分类准确率 < 50% |
| 1 | 四种人格回复几乎无法区分 |

#### C. 工具策略（7 场景）

| 分数 | 标准 |
|------|------|
| 5 | 工具调用轮数合理（≤3），结果被正确使用，无冗余调用 |
| 4 | 工具调用基本合理但有一处冗余或缺失 |
| 3 | 工具调用过多（4-5 轮），或该调的没调 |
| 2 | 明显依赖训练知识而非工具（deep 模式 0 工具），或搜索不存在条目超 5 轮 |
| 1 | 完全未调用工具，或工具结果被严重误用 |

#### D. 真实场景 & E. 边界压力

使用 A+C 的组合评分（输出质量 + 工具策略各占 50%），外加以下专项检查：
- **多轮指代**（D1-D3, E8）：是否能正确解析隐式指代和回溯引用
- **人格不崩**（E1-E3, E9-E10）：Meta 质疑和异常输入下是否守住角色
- **约束遵守**（E4-E7）：是否满足场景特定的硬约束

### 2.2 评分流程

```
1. 跑完 45 个场景，收集所有 {prompt, reply, iterations, tools_used}
2. 对每个场景，LLM-as-Judge 按维度量表评分（针对客观指标如字数，规则判断替代 LLM）
3. 人工抽查 20% 的 LLM judge 评分，校正偏差
4. 汇总：每个维度的平均分 + 总体平均分
```

### 2.3 客观指标自动检测

以下指标不需要 LLM judge，规则判断即可：

| 指标 | 规则 | 当前表现 |
|------|------|---------|
| 字数合规率 | `len(reply) ≤ WORD_LIMIT[depth] × 1.2` | ~50% |
| Deep 模式工具调用率 | `depth=deep → tools_used ≥ 1` | 50%（2/4 场景 0 工具） |
| 常识→realtime 误分类 | `intent == realtime and 查询是常识问题` | A4 |
| 空搜索最大迭代 | `search 返回空结果 → iterations ≤ 2` | 5 |
| Render 跳过率（短闲聊） | `no tools + len < 60 → render 是否被跳过` | — |

## 三、回归测试体系

### 3.1 为什么要回归测试

每次改 prompt 或调人格参数后，需要确保：
- 之前能过的场景不会退化
- 之前有问题的场景得到了改善

当前的做法是跑 `test_api_v3.sh` 然后手动对比 `test_output6.md`——太慢且容易漏。

### 3.2 方案：快照对比

```
eval/
├── data/
│   └── e2e_snapshots/
│       ├── v1_2026-07-28.json    # 45 场景的完整 {prompt, reply, metrics}
│       └── v2_2026-08-XX.json    # 修复 P0 后的新快照
```

每次重大修改后，跑一次完整的 45 场景，产出新的快照。对比脚本自动检测：

1. **退化检测**: 之前 pass 的场景现在 fail → 告警
2. **改善检测**: 之前 fail 的场景现在 pass → 报告
3. **字数漂移**: 同一场景回复字数变化 > 30% → 需要检查
4. **人格漂移**: 同一场景同一人格的关键措辞变化 → LLM judge 判断是否构成人格退化

### 3.3 简化版（v1）

不需要全自动化。最简方案：

1. 修复 P0 bug
2. 跑 `test_api_v3.sh` → `test_output7.md`
3. 手动对比 `test_output6.md` vs `test_output7.md`，列出改善项和退化项
4. 产品评测报告更新为 v2

> v1 用手动的，v2 再考虑自动化。不要过度工程化评测基础设施——先跑出数字最重要。

## 四、与简历的对应

### 4.1 修复前（不能写）

> "完成 45 场景产品评测验证人格表达一致性及输出质量"

→ 通过率 53%，面试官追问就崩了

### 4.2 修复后（可以写）

> "系统通过 45 场景产品评测，综合通过率 XX%（输出质量 X/5、人格表达 X/5、工具策略 X/5、边界鲁棒性 X/5），其中人格对比维度通过率 94%，四人格差异盲测可正确分类"

前提：
1. 总通过率 ≥ 75%
2. 人格对比维度仍然是亮点
3. 你可以诚实地说"工具策略和边界鲁棒性还在持续改进中"——这反而是一个好的面试话题（"你知道系统的弱点在哪"比"声称系统完美"更可信）

## 五、执行计划

### Step 1: 修 P0（~4h）

| 问题 | 文件 | 改动 |
|------|------|------|
| 字数控制 | `agent/persona/render.py` | render_node 输出后硬截断到 `WORD_LIMIT × 1.2` |
| Deep 不调工具 | `agent/orchestrate/nodes.py` | deep 模式的 digest hint 改为"即使是常识问题，deep 模式也必须查数据佐证" |
| 常识误分类 | `agent/orchestrate/classifier.py` | 增加纯常识问题白名单（"今天星期几"、"现在是几月"等直接 bypass intent 分类） |
| 空搜索慢 | `agent/orchestrate/nodes.py` | 搜索返回空结果后，下一轮注入"该条目不存在，不要继续搜索" |

### Step 2: 重测（~0.5h）

```bash
bash scripts/test_api_v3.sh > docs/test_output/test_output7.md 2>&1
```

### Step 3: 评分（~1.5h）

人工按 5 分制量表评分 45 个场景，汇总到新的产品评测报告。

## 六、长期愿景

当前 45 场景是**产品评测**，不是**benchmark**。长期（不是现在）可以考虑：
- 将 45 场景标准化为 `eval/data/e2e_scenarios.json`
- 场景驱动评测（每个场景有：prompt、depth、output_style、预期行为描述、评分量表）
- 最终目标：`python eval/eval_e2e.py` 一键跑完并输出报告

**但这不是优先事项。** 先修 bug、重测、拿到 ≥ 75% 的数字。自动化可以等 v2。
