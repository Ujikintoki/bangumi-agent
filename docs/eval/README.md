# Evaluation 体系文档

> **状态**: Phase 10 设计阶段 — 本文档描述待建立的评测体系
> **背景**: 2026-07-31，三位业界前辈给出简历反馈，核心问题指向同一个根因

---

## 一、诊断：为什么简历被打回来

三位前辈的反馈提炼成一句话：

> "你描述了系统长什么样，没说你的设计选择带来了什么效果。"

这不是措辞问题，是项目流程中缺失了一个阶段：

```
我们完成的：发现问题 → 设计方案 → 编码实现 → (直接跳到简历)
业界期望的：发现问题 → 设计方案 → 编码实现 → 定量评估 → 对比基线 → 简历写"提升X%"
```

每个模块都有一个未被验证的 **hypothesis**：

| 模块 | Hypothesis | 当前状态 |
|------|-----------|---------|
| RAG | "5阶段管线比 vanilla pgvector 更适合 Bangumi 冷热悬殊的数据" | 没测过 recall |
| 人格 | "5档离散查表比连续值 if-else 输出更稳定的人格" | 只有定性观察 |
| FuncCall | "三层防御闭环提高了长链路推理的鲁棒性" | 没注入过故障 |
| 记忆 | "L2 时间衰减召回能改善跨会话体验" | 没关掉 L2 做过 A/B |
| 整体 | "系统通过了 45 场景评测" | 通过率 53%，不能写进简历 |

**评测体系的本质：把每个 hypothesis 变成可验证的命题，并且真的去验证它。**

## 五、评测与简历的对应关系

做完评测后，每条简历 bullet 的变化：

**Before**（描述架构）:
> 混合 RAG 检索：设计 5 阶段检索管线——标量预过滤 → 语义分桶 → 对数归一化 → MMR 同名去重

**After**（描述成果）:
> 混合 RAG 检索：针对 Bangumi 条目冷热悬殊（最大热度差 250×）与同系列多版本共存的数据特征，设计 5 阶段检索管线。消融实验表明语义分桶+对数归一化使 recall@5 从 62% 提升至 76%（+14pp），MMR 去重贡献额外 +5pp

关键区别：前者说的是"我做了什么"，后者说的是"我做的选择有效，这是证据"。

---

## 六、核心原则

1. **每个评测必须有 baseline。** 没有对比的指标没有意义。"recall@5 = 0.76" 只有在和 "vanilla pgvector recall@5 = 0.62" 对比时才有说服力。

2. **消融实验优先于整体指标。** 面试官更关心"哪个设计贡献最大"而不是"最终数字是多少"。每个消融实验回答一个具体的"为什么"：
   - 为什么需要语义分桶？→ 因为去掉了分桶，热门作品把冷门挤出 top-5
   - 为什么需要 MMR？→ 因为去掉了 MMR，物语系列占了 4/5 个位置

3. **评测数据和代码是项目资产。** 测试集、评测脚本、实验报告全部进 git。半年后面试被问到"你怎么评价 RAG"，你可以直接说"看这个文件"。

4. **可复现 > 完美。** 评测脚本应该是 `python eval/eval_rag.py` 一键运行。如果评测结果不能被复现，它就不是科学证据。

5. **先修 bug 再评测。** 53% 的 E2E 通过率不是"需要评测总结的问题"——是需要修复的 bug。修完再测，才有资格写进简历。
