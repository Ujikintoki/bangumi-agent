# Function Calling 可靠性评测设计

> **目标**: 定量验证三层防御闭环（调用-降级-熔断）对长链路推理鲁棒性的提升
> **核心假设**: 结构化错误字典 + 指数退避重试 + 梯度熔断的组合策略，相比"抛异常即中断"的朴素方案，显著提高工具调用链路在故障场景下的任务完成率
> **预计产出**: 不同故障率下的工具调用成功率、任务完成率、平均额外迭代次数

---

## 一、问题定义

### 1.1 评测什么

当前简历描述的"调用-降级-熔断"是**架构特征**，不是**经过验证的效果**。需要回答：

> 如果 Bangumi API 挂了一部分（429 限流 / 502 网关错误 / timeout），agent 是否能继续完成用户的请求？

以及更细节的问题：
- 结构化错误字典（`{"_error": "..."}`）真的让 LLM 理解了"这个工具暂时不可用，换一条路试试"吗？
- 指数退避重试在什么故障率下仍然有效？
- 3/5/12 轮的熔断上限是否合理？是否存在"熔断得太早（放弃得太快）"或"熔断得太晚（浪费了太多轮）"？

### 1.2 当前状态

当前只有单元测试覆盖了 "API 错误被正确格式化为 `_error` dict"（`test_client.py`），但没有**故障注入实验**——没有刻意制造 API 故障来观察 agent 的恢复行为。

这个评测的独特价值：**FuncCall 可靠性是"AI 工程化"的核心关注点之一，面试官可能会问"你的 agent 在生产环境中挂了怎么办"。有故障注入实验数据，你就能回答这个问题。**

## 二、实验设计：故障注入

### 2.1 三个层级

故障注入不只在 HTTP 层。三层防御闭环的每一层都应该被独立评测：

| 层级 | 注入点 | 注入方式 | 测什么 |
|------|--------|---------|--------|
| **调用层** | 工具函数返回 `_error` dict | 修改工具 mock，直接返回 `{"_error": "service unavailable"}` | LLM 能否感知错误并切换路径 |
| **降级层** | HTTP 响应状态码 | Mock `httpx.AsyncClient`，拦截请求返回 429/502/timeout | 指数退避重试是否按预期工作 |
| **熔断层** | 连续失败 N 次 | 让某个工具持续返回错误，观察 agent 何时放弃 | 熔断上限是否合理 |

### 2.2 故障场景矩阵

| 场景 | 故障类型 | 故障率 | 持续模式 | 预期 agent 行为 |
|------|---------|--------|---------|---------------|
| S0 无故障 | — | 0% | — | 正常完成任务 |
| S1 轻微降级 | 429 | 20% | 随机 | 退避重试后成功，≤1 额外轮次 |
| S2 中度降级 | 502 | 40% | 随机 | 部分工具失败，切换到可用工具 |
| S3 重度降级 | timeout | 60% | 随机 | 大部分工具不可用，尝试绕过 |
| S4 全部不可用 | 500 | 100% | 持续 | 在熔断上限内诚实告知"服务不可用" |
| S5 间歇性故障 | mixed | 30% | 间歇 | 正确区分"暂时不可用"和"永久不可用" |

### 2.3 测试查询选择

需要覆盖不同的工具调用模式：

| 查询 | 依赖工具数 | 工具调用模式 |
|------|-----------|------------|
| "EVA 评分多少？" | 1 (search) | 单工具，故障即失败 |
| "比较巨人和鬼灭的评分和排名" | 2-3 (search ×2, get_subject ×2) | 多工具并行，单点故障可恢复 |
| "推荐和星际牛仔风格相似的动画" | 2+ (search, get_subject, search_local) | 多工具串行，有备用路径 |

## 三、指标

### 3.1 主指标

| 指标 | 定义 | 计算方式 |
|------|------|---------|
| **任务完成率** | agent 是否最终给出了满足用户意图的回复 | LLM judge 评判（0/1） |
| **工具调用成功率** | 工具调用中返回正常结果（非 `_error`）的比例 | `success_count / total_calls` |
| **平均额外迭代次数** | 因故障导致的超出正常情况的额外 ReAct 轮数 | `(total_iterations - baseline_iterations)` |

### 3.2 次指标

| 指标 | 定义 |
|------|------|
| **恢复率** | 遇到故障后成功切换路径并完成任务的比例 |
| **优雅降级率** | agent 在部分工具不可用时，是否给出了"部分数据 + 诚实告知"的回复（而非崩溃或幻觉） |
| **熔断触发率** | 是否在达到迭代上限前主动停止（好的信号——agent 意识到"搜不到了"） |
| **假阳性熔断** | agent 在工具仍可尝试时过早放弃（坏的信号） |

## 四、实现方案

### 4.1 三层 mock 架构

```
真实场景:  Agent → tool function → HTTP Client → Bangumi API
测试场景:  Agent → tool function → Mock HTTP Client (故障注入)
                                          ↓
                                    FaultInjector
                                    (按概率/规则注入故障)
```

不 mock 工具函数本身——代理仍然调用真实的 `@tool` 函数，但 HTTP 层被 mock。这样**被测的是完整的调用-降级-熔断链路**，不只是某个孤立的组件。

### 4.2 FaultInjector 设计

```python
class FaultInjector:
    """HTTP 层故障注入器。"""

    def __init__(self, fault_config: dict):
        self.config = fault_config  # {fault_type: probability}

    async def request(self, method, url, **kwargs):
        """包装 httpx.AsyncClient.request，按配置注入故障。"""
        if self._should_inject():
            fault_type = self._pick_fault()
            if fault_type == "timeout":
                raise httpx.TimeoutException("Injected timeout")
            elif fault_type == "429":
                return httpx.Response(429, headers={"Retry-After": "5"})
            elif fault_type == "502":
                return httpx.Response(502)
            ...
        # 正常请求
        return await self._real_request(method, url, **kwargs)
```

### 4.3 评测脚本架构

```
eval/
├── eval_tools.py              # 故障注入评测主脚本
│   ├── FaultInjector          # HTTP 层故障注入
│   ├── FAULT_SCENARIOS        # 6 个故障场景定义
│   ├── TEST_QUERIES           # 测试查询列表
│   └── run_experiments()      # 跑所有场景 × 所有查询
```

## 五、预期结果

### 5.1 成功标准

| 场景 | 任务完成率目标 | 说明 |
|------|-------------|------|
| S0 无故障 | 100% | 基线 |
| S1 轻微 429 | ≥ 90% | 退避重试应该解决大部分 429 |
| S2 中度 502 | ≥ 70% | 部分工具可用，agent 应切换路径 |
| S3 重度 timeout | ≥ 50% | 大部分工具不可用，但应能诚实告知 |
| S4 全部不可用 | 100%（诚实告知 = 完成） | "完成"≠"查到数据"，而是"不崩溃+告知用户" |

### 5.2 如果结果不佳

- **LLM 不理解 `_error` dict**: 如果 agent 在收到 `_error` 后仍在重复调用同一工具，说明结构化错误字典传达的信息不足。可能需要在 prompt 中增加"遇到 `_error` 时的行为规则"
- **退避重试无效**: 如果 429 场景的完成率仍然很低，检查重试逻辑是否正确读取了 Retry-After header
- **熔断太敏感**: 如果 agent 在工具第一次失败后就放弃（而实际上换个参数或换工具就能成功），说明 prompt 中的"够了就停"引导过强

## 七、与 RAG/人格评测的优先级对比

FuncCall 可靠性评测的**简历价值低于 RAG 和人格评测**。理由：
- RAG/personality 评测的数字直接挂钩用户体验（"搜索结果准不准"、"人格像不像"）
- FuncCall 评测的数字挂钩系统可靠性——面试官会认可它重要，但不如前两者直观

**建议**: RAG + personality 评测做完后，如果还有时间，再做 FuncCall。或者面试时被问到"你怎么保证系统稳定性"时，口头引用代码中的设计即可（退避重试、结构化错误、熔断逻辑），不需要必须有数字。
