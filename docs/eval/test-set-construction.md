# 评测数据集构造指南

> **适用范围**: RAG 检索评测、人格探针评测、记忆评测中的所有 ground truth 标注工作
> **核心原则**: 评测集的质量决定了评测结果的可信度。花一小时标注的评测集跑出的数字，比花十分钟标注的更有说服力——面试官追问你的标注方法论时，你能说清楚

---

## 一、通用原则

### 1.1 代表性

评测集应该覆盖你的系统**实际会遇到的各种输入分布**。一个只包含"热门动画精确名称"的 RAG 测试集会得出虚高的 recall@5，因为你的 pipeline 最难处理的冷门/模糊查询没有被测到。

**操作准则**: 画一个 2×2 矩阵，横轴是"常见/罕见"，纵轴是"简单/困难"。确保每个象限都有足够样本。

|  | 简单 | 困难 |
|--|------|------|
| **常见** | "EVA"、"巨人"（必须测，但少放） | "推荐几部好看的"（测推荐策略） |
| **罕见** | 冷门但名称明确的作品 | "80年代黑暗系机战"（核心价值） |

### 1.2 难度分层

评测集不应该全是简单查询或全是最难查询。一个健康的分布：

```
Easy（预期 recall@5 > 0.8）:    ~30%  精确作品名、热门角色名
Medium（预期 0.5-0.8）:         ~40%  模糊描述、跨类型查询
Hard（预期 0.3-0.5）:           ~30%  冷门作品、模糊边界查询
```

如果 easy 查询的 recall 也低 → embedding 模型有问题
如果只有 hard 查询低 → pipeline 在极端情况下变弱（预期之内）
如果所有都一样高 → 评测集太简单，没有区分度

### 1.3 规模

| 评测目标 | 最小量 | 推荐量 | 理由 |
|---------|--------|--------|------|
| RAG 检索 | 40 | 60 | < 40 统计不显著；> 100 标注成本过高 |
| 人格探针 | 16 | 20 | 4 种人格 × 4 类别，每类至少 4 条 |
| L1 记忆 | 1（10 轮脚本） | 1 | 不需要多条——一个精心设计的脚本就够了 |
| L2 记忆 | 6 会话 | 9 会话 | 3 主题 × (2-3 会话) |

### 1.4 版本管理

评测数据集一旦稳定，**不要随意修改**。修改评测集会让你失去跨版本的对比能力。

```
eval/data/
├── rag_queries_v1.json    # 第一版，60 条
├── rag_queries_v2.json    # 如果以后扩充到 100 条，新建 v2
```

每个版本的评测数据集附带一个 `_NOTES.md` 说明：
- 什么时候创建的
- 查询来源（手工编写 / Bangumi 搜索日志 / 用户反馈）
- ground truth 标注方法（人工 / 自动化 / 混合）
- 已知的局限性（"v1 缺少 NSFW 查询的覆盖"）

## 二、RAG 测试集标注

### 2.1 查询生成

**不要只用你脑子里想出来的查询。** 这会导致评测集偏向你熟悉的查询模式。三条补充来源：

1. **产品评测日志** — `docs/test_output/` 中的 45 个场景里至少有 10 个好的 RAG 查询（A1-A8, C1-C7, D1-D8）。直接复用
2. **Bangumi 搜索建议** — 在 bangumi.tv 搜索框里随便打字，看下拉建议。这些都是真实用户的搜索模式
3. **边界案例手动构造** — 你比普通用户更了解系统的弱点（bare title、模糊边界、跨类型混淆），针对性构造这些查询

### 2.2 Ground Truth 标注流程

```
Step 1: 在 rag_entities 表中确认候选条目存在
  SELECT id, name, name_cn, entity_type FROM rag_entities
  WHERE entity_type = 'subject' AND name_cn LIKE '%EVA%';

Step 2: 在 Bangumi 网站上搜索 query text
  确认地面真实：这些条目在 Bangumi 上确实被用户认为是相关的

Step 3: 给每个查询标注 3-5 个 ground truth entity_ids
  原则：如果一个真实的 Bangumi 用户在搜索结果中看到这个条目会认为相关 → 它是 ground truth

Step 4: 标注 category（A/B/C/D/E）
  用于后续的分类型分析

Step 5: 记录 notes
  标注过程中的任何疑惑、边缘决策都记录下来
```

### 2.3 常见陷阱

| 陷阱 | 说明 | 避免方法 |
|------|------|---------|
| **确认偏误** | 标注时已经看了 RAG 的返回结果，不自觉地认为"RAG 返回的应该就是正确答案" | 先标注 ground truth，再看 RAG 结果 |
| **标注过宽** | 把 ground truth 标了 10 个——"只要是这个类型的都算对" | 最多标 5 个，想象你是在给用户推荐 top-5 |
| **标注过窄** | 只标了 1 个——"只有这一个才是正确答案" | 对于模糊描述查询，多个条目都可能正确 |
| **记忆偏误** | 只标你熟悉的、有名的作品 | 搜索 Bangumi 确认，不要只凭记忆 |
| **版本漂移** | 标注时用的条目评分和 RAG 检索时的评分不同 | 标注时记录评分快照，评测时如果评分变了 > 20%，重新检查 ground truth |

## 三、人格探针标注

### 3.1 探针的"好"标准

一条好的人格探针：

1. **有态度空间** — "EVA 哪年播的" 不产生人格差异；"EVA 是不是过誉了" 会产生
2. **在 Agent 的能力范围内** — 探针涉及的话题应该是 agent 能讨论的（ACGN 领域）
3. **不是 prompt injection** — 不需要刻意测试 "ignore all previous instructions" 这类攻击
4. **有明确的目标人格差异化预期** — 在写探针时，你应该能预测四种人格会给出不同的回复

### 3.2 预期行为标注

每条探针标注**每种人格的预期行为**（不是预期输出，而是预期态度/策略）：

```json
{
  "id": "p001",
  "text": "EVA是不是被过誉了？",
  "expected_behavior": {
    "bangumi": "部分肯定部分反驳，有态度的分析",
    "bangumi_cold": "直接否定'过誉'的说法，可能纠正前提错误（EVA不是机甲）",
    "bangumi_cute": "温和解释为什么EVA值得这个地位，不反驳用户",
    "neutral": "数据驱动，展示评分和排名，让用户自己判断"
  },
  "discriminative_power": "high",
  "category": "争议评价"
}
```

`discriminative_power`（区分力）是对探针质量的自我评估：
- `"high"`：四种人格应该有非常不同的回答
- `"medium"`：有些人格之间可能接近
- `"low"`：探针可能不产生明显人格差异（但仍应测试）

**目标**: 至少 75% 的探针为 "high" 区分力。

## 四、标注质量保证

### 4.1 自检清单

每个评测数据集完成后，回答以下问题：

- [ ] 如果另一个 Bangumi 重度用户看这个查询+ground truth 对，会同意 ground truth 的选择吗？
- [ ] 评测集包含了系统最可能出错的查询类型吗？（不只是最擅长的）
- [ ] 有没有至少 20% 的"困难"查询来防止天花板效应？
- [ ] 每个查询的 ground truth 条目都在 `rag_entities` 表中吗？
- [ ] 查询文本本身是否像真实用户会输入的？（不是工程师式的"请检索评分>8.0且类型为动画的条目"）

### 4.2 标注一致性（未来）

v1 评测集由你一个人标注——可以接受。但面试时如果被问到"你怎么保证标注质量"，可以参考：

> "v1 评测集由我根据 Bangumi 网站搜索结果标注，确保 ground truth 反映真实用户期望。未来如果有多人标注资源，可以计算标注者间一致性（Cohen's κ）来验证标注质量。"

## 五、维护策略

### 5.1 何时更新评测集

| 触发条件 | 操作 |
|---------|------|
| `rag_entities` 表大规模更新（新增 > 1000 条目） | 重新检查 ground truth 是否需要更新 |
| 嵌入模型切换（如 Zhipu embedding-3 → 新模型） | 重新跑全部评测，对比新旧嵌入模型 |
| 发现某个类别（如冷门作品）样本量太小 | 新增该类别查询，发布 v2 |
| 用户反馈中出现了新的查询模式 | 收集为新的评测查询 |

### 5.2 何时**不**更新

- **不要为了"好看的数字"修改评测集**。如果 RAG 的 recall 低，应该改进 RAG，而不是把那些"导致低 recall"的查询删掉
- **不要在评测结果出来后再调整 ground truth**。如果 ground truth 确实错了，应该修正——但要在报告中注明"原始标注存在偏差，v2 修正了 X 条 ground truth"

## 六、工具推荐

| 任务 | 工具 | 用途 |
|------|------|------|
| 查询生成 | 脑力 + Bangumi 搜索框 + `docs/test_output/` | 保证多样性 |
| Ground truth 查找 | `psql` 查 `rag_entities` + bangumi.tv 搜索 | 验证条目存在且相关 |
| JSON 编辑 | VS Code | 格式校验和自动补全 |
| 版本对比 | `git diff eval/data/rag_queries_v1.json` | 追踪评测集变化 |

不需要复杂的标注工具或平台——对 60 条查询的评测集来说，手写 JSON + VS Code 是最快的方案。
