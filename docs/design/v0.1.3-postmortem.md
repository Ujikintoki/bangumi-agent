# v0.1.3(beta) Postmortem — 分离合成架构实验

> 基于两次独立压测（Run 1: 212728, Run 2: 213823）的对比分析。
> 标记 ✅ = 有数据支撑的确定结论。⚠️ = 推断但缺少关键数据。❓ = 纯推测。

## 架构背景

BGM Agent 是 Bangumi 站内的 Companion Agent。v0.1.3 实验分离合成架构：

```
Aggregator LLM (数据收集, tools) → submit_facts_to_render → Render LLM (人格表达)
```

两层之间代码层做 JSON→Markdown 确定性拼接。技术栈：FastAPI + LangGraph StateGraph + DeepSeek function-calling。

## 核心发现：同一套代码、同一个 case、两次完全不同的结果

| Case | Run 1 | Run 2 |
|------|-------|-------|
| B2: 2011年8.5+作品 | 编造 HxH 8.2、漏 Steins;Gate ❌ | 四部全对：S;G 8.85、银魂' 8.71、小圆 8.58、日常 8.5 ✅ |
| B3: 香菜角色 | "千石抚子不是她配的" ❌ | 千石抚子、黑猫、立华奏…全对 ✅ |
| B1: Monster 评分 | "8分出头"（模糊） | "8.23分"（精确） |
| C2: 氛围推荐 | 泄漏 Aggregator 内部文本 43 字 ❌ | 正常回复 319 字 ✅ |
| B3: 迭代数 | 6 轮 | 10 轮（更差） |

**结论：这些问题不是架构级 bug。它们是模型行为的不确定性。** 同一 prompt、同一工具、同一代码路径，两次采样结果截然不同。

## 问题 1：事实性错误 — ✅ 根因确定：模型在 summary 字段中自由发挥

### 确定结论
- **不是工具返回了错误数据**。两次压测用同一批工具，B2/B3 在 Run 2 得到正确答案说明工具是可靠的。
- **不是意图分类错误**。intent 在两次都是正确的（B2/B3=lookup, C3=discovery）。
- **是模型在填 `submit_facts` 的 `summary` 字段时，paraphrasing 过程中混入了自身训练知识。** 尤其当工具返回的数据不完整或需要提取时，模型倾向于"补全"而非"留白"。

### 不确定的部分
- 工具到底返回了多少数据？哪些字段被正确使用、哪些被编造？没有原始 ToolMessage 日志。
- 模型是否在消化阶段就产生了幻觉（content 文本），还是只在 summary 中填错了？无法区分。

### 代码落点
- `agent/orchestrate/prompt_builder.py` `_AGGREGATOR_IDENTITY`：缺少"summary 只能改写工具返回内容，不得添加任何工具未返回的信息"
- `schemas/tools_input.py` `FactItem`：无字段级约束（如 source 字段必须对应实际调用的工具名）

### 不确定
- 加了数据诚信护栏后能好多少？Run 2 已经对了大多数，Run 1 错了很多——说明 prompt 护栏有一定效果但不稳定。
- 是否需要在代码层做交叉校验（facts 中的 score 与 ToolMessage 中的 API 返回值比对）？成本不低，需要先确认收益。

## 问题 2：响应时间 — ✅ 根因确定：串行 ReAct 迭代数过高

### 确定结论
| 压测 Case | 工具数 | 每轮 LLM 推理 (~3-8s) | 估算总时间 |
|-----------|--------|----------------------|-----------|
| auto 4 轮 | 3-6 工具 | 4 次 LLM | ~12-32s |
| auto 5 轮 | 4-6 工具 | 5 次 LLM | ~15-40s |
| B3 (Run 2) 10 轮 | 6 工具 | 10 次 LLM | ~30-80s |
| C3 deep 7 轮 | 4 工具 | 7 次 LLM | ~21-56s |

**每多一轮就多一次 LLM 推理等待。** 这是响应时间长的主要原因。模型不总是听从"够了就提交"的指令——B3 在 Run 1 跑 6 轮、Run 2 跑 10 轮。

### 不确定的部分
- 每次 LLM 推理的实际耗时？单次 ToolNode 执行耗时？没有 DEV_MODE 计时数据。
- 网络延迟占多少？

### 代码落点
- `agent/graph.py`：`reasoning_node ⇄ tool_node` 串行循环，无并行
- `agent/orchestrate/prompt_builder.py` `TOOL_GUIDANCE`：有"detail+opinions+characters 必须同一轮并行"的指引，但模型不总是遵循
- `agent/state.py` `_MAX_ITERATIONS_*`：auto=5 不够用（B3 跑 10 轮说明没有硬截断——10>5！）

### 需要查证
**B3 Run 2 跑了 10 轮但上限是 5？** 这说明 `_LAST_CHANCE_INSTRUCTION` 没有真正阻止继续调用工具。需要查 `nodes.py` 的终止逻辑——应该是 prompt 指令而非硬截断，模型可以无视。

## 问题 4：文本泄漏 — ✅ **已修复 (f53d359)**

### 确定结论
Run 1 C2 泄漏 43 字，Run 2 同一 case 正常。泄漏内容是 Aggregator 内部独白（"核心数据已到手。为做出真正的推荐而非标签匹配，我拉取最强候选的口碑数据来支撑推荐理由。"）。

### 泄漏链路（已堵死）
1. DeepSeek 在最后一轮同时产生 AIMessage.content 和 tool_calls=[submit_facts_to_render]
2. ToolNode 正常执行 → ToolMessage
3. Graph 结束 → main.py 找到 submit_facts ToolMessage → force_render=True
4. ~~Render LLM 调用失败（或返回 <5 字符）~~
5. ~~`rendered` 为 None → 代码跳过 `_replace_last_ai_content`~~
6. ~~`_extract_final_reply` 找到 Aggregator 的 AIMessage → 泄漏~~

### 修复方法
**`main.py:440-444` + `main.py:580-583`** — Render 失败 + submit_facts 路径时，不再 fallback 到 Aggregator 的 AIMessage.content，而是降级为 `_build_render_input` 产生的确定性 Markdown。

```python
# 修复前：Render 失败时什么都不做 → Aggregator 内部文本泄漏
if rendered:
    result["messages"] = _replace_last_ai_content(messages_for_render, rendered)

# 修复后：Render 失败时降级为确定性 Markdown
if rendered:
    result["messages"] = _replace_last_ai_content(messages_for_render, rendered)
elif facts_json is not None:
    # submit_facts 路径 + Render 失败 → 降级为确定性 Markdown
    # 绝不 fallback 到 Aggregator 的 AIMessage.content——那是内部草稿本
    result["messages"] = _replace_last_ai_content(messages_for_render, render_input)
```

**原则**：Gemini 指出的 "Aggregator 的 content 是草稿本，绝不展示给用户"。两个端点（`/chat` 和 `/chat/stream`）均已修复。

## 问题 5：迭代耗尽 — ✅ **已修复 (f53d359)**

### 确定结论
D1 Run 1: 5 轮耗尽 → "查询达到最大处理轮次"。B3 Run 2 跑 10 轮远超 auto=5 上限。

根因：`_LAST_CHANCE_INSTRUCTION` 只是追加到 System Prompt 末尾的文本——"大模型是不会自己数数的"（Gemini）。模型完全无视它继续调工具，graph 的 `route_after_tool` 也只看最后一个 ToolMessage 是不是 submit_facts，不看 iterations。

### 修复方法
**`agent/graph.py:57-68`** — `route_after_tool` 顶部增加代码级硬熔断，与 prompt 完全无关。

```python
# 修复前：只检查 submit_facts，不检查迭代次数 → 模型可以无限循环
def route_after_tool(state):
    if last_tool_message == "submit_facts_to_render":
        return END
    return "reasoning_node"

# 修复后：迭代上限优先于一切
def route_after_tool(state):
    # 硬熔断：迭代上限是代码级强控制流
    if current_iter >= max_iter:
        return END  # 不跟模型商量

    if last_tool_message == "submit_facts_to_render":
        return END
    return "reasoning_node"
```

`route_after_reasoning` 不需要同样处理——因为硬熔断在 `route_after_tool` 中，模型调用工具后立即被截断。非 deep 模式若最后一次 reasoning 输出 tool_calls → tool_node 执行 → route_after_tool 硬截断 → END。此时 `main.py` 用已有数据组装 Markdown（可能是半成品，但好过错误消息）。

## 待修复 (P1)

### P1-1: Schema 硬约束 — 从"总结"转向"抽取"

**根因**：Gemini 指出，让 LLM 在 `summary` 字段做 paraphrasing 是幻觉的根源。LLM 生成自然语言时会被训练权重"带偏"。

**方案**（两步，按收益/成本排）：

**Step A — Prompt 级（低风险，先做）**
修改 `FactItem.summary` 的 description：
```python
# schemas/tools_input.py
summary: str = Field(
    default="",
    description="直接摘抄 API 返回的原文片段，绝对禁止用自己的话概括或改写。如果没有原文，留空。不超过 200 字。"
)
```
同时在 `_AGGREGATOR_IDENTITY` 中加一句："summary 字段中只放工具返回的原文——不要 paraphrase、不要总结、不要补全。"

**Step B — 代码级校验（中等风险，Step A 不够时再做）**
在 `main.py` 的 `_build_render_input` 之后、调用 Render 之前，比对待提交的 facts：
- `facts[].score` 是否在原始 ToolMessage 中出现？
- `facts[].source` 是否对应实际调用的工具名？
- 不匹配的字段 → 丢弃或用 `"（数据未核实）"` 替代

成本：需要维护工具返回字段的映射表。收益不确定——Step A 可能已经够了。

### P1-2: 并行工具调用指引强化

**根因**：`TOOL_GUIDANCE` 已有"detail + opinions + characters 必须同一轮并行"的指引，但模型不总是遵守。

**方案**：
- 在 `TOOL_GUIDANCE` 中将并行指引从一段文字改成强制格式（如 `## 本轮必须执行` 列表）
- 在消化态 hint 中增加：`"拿到 subject_id 后，除非你打算提交，否则必须将 detail/opinions/characters 作为同一轮 tool_calls 并行调用"`
- 验证：跑压测对比修复前后的平均迭代轮数

预期效果：将 "搜番→详情→评论" 从 3 轮压缩为 2 轮，auto 模式从平均 4 轮降至平均 2-3 轮。

### P1-3: Render 失败重试

**根因**：`render_reply` 的 LLM 调用是单次尝试，异常直接 return None。

**方案**：
- `render_reply` 中 LLM 调用加 1 次重试（共 2 次），间隔 1s
- 两次都失败 → 降级为 Markdown（P0-2 的兜底）

成本极低，`main.py` 中 `render_reply` 调用方已有兜底逻辑。
