# 开发者预览版发布计划

> 2026-07-28 | 目标：让第一批真实 Bangumi 用户用上 BGM Agent

---

## 一、诚实评估：现在能发布吗？

**能，但不是"产品发布"——是"开发者预览版"。**

| 维度 | 当前状态 | 能见人吗 |
|------|---------|---------|
| 人格表达 | 4 种人格差异清晰，角色一致性高（8/10） | ✅ 最大的卖点 |
| 短程对话 | 1-3 轮准确，工具使用基本合理 | ✅ 够用 |
| 字数控制 | auto 模式近半数回复超标 | ⚠️ 用户会感知到"话太多" |
| 长程记忆 | 8 轮后完全失忆 | ⚠️ 深度用户会触发 |
| Deep 模式 | 偶尔不调工具，闭卷答题 | ⚠️ 高级功能不稳定 |
| 基础设施 | 无鉴权、无限流、无监控 | ⚠️ 能跑但裸奔 |

**结论：不要假装这是成品。** 把它标为"开发者预览版"，主动告知已知问题，邀请 Bangumi 用户来玩而不是来用。正确的预期管理比修完所有 bug 更重要。

---

## 二、发布策略：分两阶段

### 阶段 1：内部可控发布（本周可做）

**目标**：10-30 个信任用户，验证核心假设

**假设清单**（发布后需要回答的问题）：
1. H1: 用户会选择非默认人格吗？（bangumi_cold / bangumi_cute 的使用率）
2. H2: 用户更常用哪个 depth？（auto vs quick vs deep 的比例）
3. H3: 用户遇到的最大痛点是什么？（字数太长？答非所问？太慢？）
4. H4: 用户会进行多轮对话还是单轮查询？（影响 L1 预算分配）
5. H5: 人格差异用户能感知到吗？（切人格后用户留存/回切行为）

**用户筛选**：
- 从 Bangumi 论坛/群组邀请 10-30 个活跃用户
- 优先选看过 100+ 部作品、写过短评的用户（他们有判断力）
- 每人给一个唯一的 `user_id`，用于追踪使用模式

### 阶段 2：公开预览版（2-3 周后）

**目标**：所有 Bangumi 用户可访问，收集规模化数据

前提：阶段 1 的 H1-H5 有明确答案，P0 问题修了至少 2 个。

## 三、阶段 1 需要做的事

### 3.1 必须做（否则不能发）

#### ① 加基础限流

没有限流 = 一个用户死循环 deep 模式就能打挂服务。

```python
# main.py — 最简单的 IP 级别限流
from fastapi import Request
from collections import defaultdict
import time

_request_log: dict[str, list[float]] = defaultdict(list)

async def rate_limit_middleware(request: Request, call_next):
    ip = request.client.host if request.client else "unknown"
    now = time.time()
    # 每个 IP 每分钟最多 10 个 /chat 请求
    _request_log[ip] = [t for t in _request_log[ip] if now - t < 60]
    if len(_request_log[ip]) >= 10:
        return JSONResponse({"error": "太快了，休息一下"}, status_code=429)
    _request_log[ip].append(now)
    return await call_next(request)
```

#### ② 加错误告警（最低限度）

当前"服务挂了"只有 uvicorn 日志。至少加一个 health check endpoint 被外部监控。

已经有了 `/health`。需要有人（或 cron）每分钟 ping 一次，挂了就通知。

#### ③ 创建"开发者预览版"提示

用户第一次打开时，看到一段话：

> **开发者预览版**
> 
> 这是 BGM Agent 的早期测试版本。她有时候会：
> - 话说太多收不住（字数超标）
> - 聊久了忘记前面说过什么
> - 深度模式下偶尔偷懒不查数据
> - "今天星期几"这种问题调用日历 API（是的这是个 bug）
> 
> 如果你发现了有趣的行为或 bug，欢迎反馈：[反馈入口]
> 人格切换试试 `output_style` 参数：bangumi / bangumi_cold / bangumi_cute / neutral

#### ④ 反馈收集机制

最简单的方案：一个 Google Form 或 GitHub Issue 模板，包含：
- 你用了哪个人格？
- 问了什么问题？
- 她的回答哪里好/哪里不好？
- 截图

### 3.2 应该做（提升体验）

#### ⑤ 简单前端

当前只有 `curl` 命令可以调用。需要一个最小前端：

**方案 A（推荐）**：纯 HTML 页面嵌入 Bangumi 站内
- 一个聊天框 + 人格选择下拉菜单 + 深度选择
- ~200 行 HTML + vanilla JS，无需框架
- 直接 POST 到 `/chat` 端点
- 部署为静态文件或 FastAPI 静态路由

**方案 B**：Telegram/Discord Bot
- 最快让用户触达的方式
- 用户在群里 @bot 就能聊
- 但失去了 Bangumi 站内场景

**方案 C**：油猴脚本
- 用户在 Bangumi 页面右下角看到一个聊天窗口
- 跟 `docs/tmp/UserScriptAi.js` 参考的油猴脚本模式一致
- 最贴合"住在 Bangumi 站内"的定位

#### ⑥ Dev mode 数据收集

利用已有的 `DEV_MODE=true` + telemetry，记录：
- 每种人格的使用次数
- 每种 depth 的使用比例
- 平均迭代轮数
- 工具调用频率分布
- 平均响应时间

不需要用户系统——完全匿名。这些数据用于验证阶段 1 的 H1-H5 假设。

### 3.3 最好做（p0 问题）

从产品评测中挑 1-2 个能快速修的问题：

#### ⑦ 字数控制快速止血（1-2 小时）

在 render_node 输出后加硬截断：

```python
# render.py — render_node 返回前
max_chars = {"quick": 150, "auto": 250, "deep": 450}[depth]
if len(rendered) > max_chars:
    # 在最后一个完整句子处截断
    cut = rendered[:max_chars].rfind("。")
    if cut > max_chars // 2:
        rendered = rendered[:cut+1]
    else:
        rendered = rendered[:max_chars] + "…"
```

#### ⑧ 搜索空结果快速放弃（30 分钟）

在 `orchestrate/guardrails.py` 或 `nodes.py` 中，搜索空结果 2 轮后注入终止指令：

```python
if consecutive_empty_searches >= 2:
    messages_for_llm.append(HumanMessage(
        content="（系统指令：已连续 2 次搜索无结果。该条目很可能不存在于 Bangumi 数据库中。直接告诉用户没找到，不要继续搜索。）"
    ))
```

## 四、具体行动计划

### Week 1（现在-3 天）：基础设施 + 止血

| 天 | 任务 | 产出 |
|----|------|------|
| 1 | 限流中间件 + 日志持久化 | `main.py` +20 行 |
| 1 | 字数硬截断 | `render.py` +15 行 |
| 2 | 空搜索快速放弃 | `nodes.py` +10 行 |
| 2-3 | 最小前端（HTML 聊天框） | `static/index.html` ~200 行 |

### Week 1-2：邀请第一批用户

| 天 | 任务 |
|----|------|
| 3 | 在 Bangumi 发帖招募 10-30 个测试用户（附开发者预览版说明） |
| 3-7 | 观察使用数据，每天看日志，收集反馈 |
| 7 | 整理第一周反馈，判断 H1-H5 假设 |

### Week 2-3：根据反馈迭代

基于阶段 1 数据决定优先级：
- 如果 P0 问题（字数/记忆/deep）被大量反馈 → 优先修
- 如果人格切换使用率极低 → 优化前端或默认人格
- 如果用户只做单轮查询 → 减少多轮投入

## 五、不要做的事（现在不需要）

| 不要做的事 | 原因 |
|-----------|------|
| 用户注册/登录系统 | 开发者预览版不需要——用 `user_id` 参数区分即可 |
| HTTPS/域名/部署 | 内测阶段本地跑或内网部署足够 |
| 数据库持久化 session | 内存缓存 1 小时 TTL 够用了 |
| 正式的 SLA/运维 | 这不是产品发布 |
| 完整的前端 SPA | 聊天框够用了 |
| P0 全部修完再发 | 修不完。带 bug 发，收集反馈比闭门修 bug 更快 |
| 性能优化 | 还没到瓶颈 |

## 六、成功标准

阶段 1 成功的标志（不需要全部达到，但至少 3/5）：

1. **10+ 用户一周内至少使用了 3 次以上**（不是尝鲜就跑）
2. **至少 5 条有质量的反馈**（不是"挺好的"，是"XX 场景下她说了 YY，我觉得 ZZ"）
3. **至少 1 个用户切换了非默认人格并持续使用**（证明人格差异化有价值）
4. **没有因服务崩溃导致的严重负面体验**（偶尔答错可以，服务挂了不行）
5. **H1-H5 至少 3 个有明确答案**（知道下一步该往哪走）

## 七、风险与缓解

| 风险 | 概率 | 缓解 |
|------|------|------|
| DeepSeek API 费用失控 | 中 | 限流 + deep 模式加独立频率限制 |
| 用户期待过高，差评 | 高 | 主动标注"开发者预览版" + 已知问题说明 |
| Bangumi API 被限流 | 低 | 当前每用户每分钟 10 次 /chat，工具调用有 16 工具限制 |
| 没人用 | 中 | 主动邀请而非等用户来；选对人比选多人重要 |
| 出 bug 不知道 | 中 | 日志打到文件 + health check 监控 |
| 敏感话题回复不当 | 低 | 已有 guardrails；开发者预览版用户基数小 |

---

## 八、总结

**现在可以发布，但必须是"开发者预览版"——主动降预期、带已知问题、找对用户。**

不需要等到"所有 P0 都修完"——那可能需要几周，而这几周里你会错过最宝贵的东西：**真实用户的反馈**。与其闭门造车修 bug，不如让 10 个真实用户告诉你哪个 bug 最痛。

优先级：**限流 + 前端 + 反馈入口 > 字数止血 > 其他 P0 修 bug > 新功能。**
