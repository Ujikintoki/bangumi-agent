# 代码现状盘点委托

> 状态：第一轮系统盘点已交付；追加第二轮 Agent 设计盘点，2026-10-28。
> 本文规定盘点范围和交付物，不是功能 backlog 或实施计划。执行结果另存定时点报告。

## 目标与产品依据

对 main 当前工作区开展系统级静态审查与隔离动态验证，为第一版范围取舍提供证据。
先读 AGENTS、PRODUCT、ROADMAP、README 和架构蓝图中的开工四问。历史资料按文档地图使用。
主要任务是实体识别、事实查询、连续口碑/情绪讨论和按需整理短 comment。
系统工程与 AI/LLM/Agent 设计具有同等审查地位，分别交付证据，并核对两者的交接。
不优化人格文案，不扩展候选功能，不在审查中开始修理；避免将“不调人格语气”理解为“不审查 Agent 设计”。

最新已确认交付：独立网页主入口 + 用户自运行个人实例，默认本机启动、用户自备模型 API。
Bangumi 站内组件为希望尝试的副入口，不作为第一版交付前提；不预设网页可以自动读取当前 Bangumi 页面。
主要按用户输入名称、提供链接或粘贴文本评估实体/材料接入，页面对象与选文接入另列副入口扩展成本。
状态能力与组件范围待盘点后取舍；项目方运营多人共享服务不作为第一版目标。
第一轮按当时未定方案进行的比较保留为历史证据；第二轮按当前产品方向分析，不要求重写第一轮报告。

## 工作区与输出边界

- 记录 HEAD、工作区未提交/未跟踪变更清单、环境和审查范围；工作区现状才是检查对象。
- 保留现有修改，不清理、不提交、不切分支，不修改业务代码、配置、依赖或历史报告。
- 允许在临时目录编写最小复现。第一轮报告为 `docs/codebase-inventory-report.md`；
  第二轮只新增 Agent 设计报告（文件名和要求见下文），保留第一轮内容，不覆盖其基线和结论。
- 不读取 `.env` 或输出凭据。遵守 AGENTS 的受保护目录和真实数据库禁用边界。
- 不因审查需要自动启动当前服务：先检查启动、配置加载和 lifespan 是否会连接数据库或执行迁移。

## 静态盘点

追踪主要路径与模块边界，而非只列文件和代码风格问题：

1. HTTP 输入、身份绑定、session 归属、普通/SSE 路径、取消与整轮生命周期。
2. 路由、Pipeline/ReAct、工具与 HTTP 客户端、来源整理、上下文装配、最终渲染和失败交接。
3. 当前对象、材料、纠正和偏好怎样流动；L1、L2、持久化与会话恢复的真实边界。
4. 数据库依赖、初始化/迁移、副作用、配置与凭据管理、依赖和启动交付。
5. 前端/组件资产、测试、日志、文档和许可；标出存在、可复用、缺失、未经验证及仅本机可得。
6. 删除候选必须有当前引用、动态注册/兼容职责和测试覆盖证据；无法证明时列为待核验，不删除。

## 动态验证

- 先用 `scripts/test_offline.py` 运行审阅过的测试；缺缓存或依赖时记录限制，不改依赖或擅自下载来绕过。
- 在阻断外部网络与真实数据库的前提下，用固定材料和替身验证核心路径。
  可补临时复现，不扩大未经审阅的全量测试执行。
- 覆盖连续三场景、用户纠正、对象歧义、空材料、超时/工具/模型失败、未知来源、预算截断。
- 检查 JSON/SSE 一致性、取消/异常后的锁释放、同会话并发和不同会话隔离；
  检查服务重启后状态是否恢复。没有相应能力时记录缺口，不通过临时补实现制造通过。
- 数据库集成只有在明确隔离且可证明不接触既有数据时执行；否则列为未验证。
  本任务不默认授权付费模型调用或真实 API 测试；需要时列出具体补验方案与必要条件。
- 区分固定材料验证、真实服务证据与旧报告。HTTP 200、工具成功或单元测试通过，不代表产品任务完成。
- 检查日志与报错是否泄露凭据或私人材料；报告只保留脱敏证据。

## 报告必须包含

1. 执行摘要、基线、静态覆盖清单、动态命令/结果、失败与未执行项及原因。
2. 真实请求与状态流转图，现有模块责任和依赖问题；关键事实给文件、符号或行号。
3. 问题清单：触发条件 → 用户/运行影响 → 证据 → 根因或假设 → 置信度 → 修复方向。
   不为未选定的托管能力缺失直接报当前缺陷，分别标记产品缺口、条件性需求与代码错误。
4. 候选交付差异：哪些可复用，哪些需新增设计，哪些阻碍交付；不替用户决定入口。
5. 状态能力矩阵：会话隔离、历史保存、重启续聊、会话删除、长期偏好、主动追踪和跨设备访问。
   每项说明使用收益、已有资产、缺口、依赖、设计/实现/测试/持续维护成本、替代方案和估计置信度。
   成本用低/中/高及理由；估时如确有依据，标注假设，不给伪精确的人天承诺。
6. 删除候选及反证、重要未验证项和最小补验条件。
7. 最后提出范围取舍建议，明确等待用户与主线讨论；不直接生成排期，不开始修复。

## 完成条件

全部静态领域和动态场景均有覆盖结果或明确未覆盖原因；关键结论可追溯到证据；
投入/回报评估足以支持交付与状态范围的下一轮决策。结束时核对工作区，证明没有改动业务文件。
全仓盘点不等于证明系统没有其他缺陷。

## 第二轮：AI/LLM/Agent 设计专项（同等地位）

### 目标与复用边界

先读取第一轮报告并核对其代码基线、当前工作区和产品变化。复用已验证的系统事实，
仅在新问题依赖它或代码已变时复验；不机械重复第一轮全部测试。
本轮独立判断 Agent 设计是否支撑 PRODUCT 的真实任务，而非只检查框架是否接通。
模型能力、输入信息、工具结果、上下文装配、控制流和最终表达需要分开定位，不能全部归因于 prompt。

### 必须覆盖的设计领域

| 领域 | 需要回答的问题 |
|---|---|
| 模型与调用配置 | 分类、推理、合成、Render、摘要、embedding 各用什么配置、结构化约束与预算？用户自备 API 的工具调用/输出协议有哪些真实假设？配置存在不等于兼容已经验证 |
| 意图与实体 | 分类实际看哪些信息？代词、纠正、情绪、材料输入、复合任务如何处理？页面对象与用户显式提及另一对象冲突时如何选？置信度与路由语义是否匹配 |
| 规划与控制 | Pipeline/ReAct 分工是否有依据？多目标查询、补充取证、重试、重复调用与结束怎样决定？执行结束与用户任务完成是否分离；不预设需要重写拓扑或增加 Agent |
| 工具与数据表达 | 名称、描述、参数、白名单、tool_choice、返回 schema 是否使正确选择可行？缺参、歧义、空结果、部分失败如何进入模型？comments/reviews/board 的语义与引用粒度是否保留 |
| Context engineering | 列出各模型调用最终实际收到的消息/工具/schema、拼接顺序、来源与信任等级、预算和截断规则；检查重复、冲突、丢失与无关信息，不仅数 prompt 文件长度 |
| 状态与记忆 | 活动对象、用户纠正、观点、剧透范围、临时偏好与长期偏好的表示和寿命；压缩是否丢掉关系/来源/立场，L2 写入与召回是否符合授权语义、相关性和时效 |
| RAG 与外部证据 | 触发、实体匹配、检索结果与原文范围、证据覆盖、冲突和时效怎样影响判断？不读取受保护语料，不从检索函数存在推断质量合格 |
| 判断与 Render | 原始工具数据如何变成判断再成为最终回复？是否丢掉缺口、扩大样本、混淆用户/他人观点或加入无依据断言？引用机制覆盖不了什么？检查人格指令的功能冲突，不做审美改写 |
| 任务与信任边界 | 页面/评论中的指令是否会变成系统指令？公开材料、用户授权与候选动作如何区分？关注现有数据链上的具体风险，不扩成无场景的安全项目 |
| 可观测性与评测 | 能否定位错误发生在哪一阶段？质量证据、工具成功、HTTP 成功怎样区分？调用数、预算、重复取数、Render 的成本与收益有哪些实测或明确未知 |

对“prompt 厚重、系统单薄”的疑虑给出证据：哪些任务规则只写在提示中却缺少程序状态或契约，
哪些规则适合保留给模型判断，哪些信息被重复传递却没有可见收益。不能仅凭行数或 token 长度下结论。
不要求暴露或采集模型隐藏思维链；只检查可观察的消息、工具调用、结果和状态。

### 动态验证与证据强度

延续原委托的网络、数据库、凭据与不修改代码边界。使用合成材料，不读取受保护评测集。
先建立覆盖表，再选择有区分力的最小复现：

- 原三个连续场景，加“把我的观点梳理成短 comment”的明确请求。
- 同一句代词/情绪输入在不同前文、不同对象下；混合查询；用户纠正立场或实体；切换对象。
- 不同来源相互冲突、只有 review 摘要、空结果、只完成部分维度；验证证据和缺口进入各阶段。
- 长材料与历史压缩前后，关键纠正、来源、剧透范围是否仍可见；材料中夹有恶意指令的信任边界。
- 工具返回畸形内容/异常、模型无效结构/无正文、重复调用、预算耗尽与过早结束。

必须明确区分：

1. 静态代码事实：证明存在什么路径或条件，不能证明模型实际表现。
2. 固定/脚本化模型与工具：证明信息交接、协议和控制流；不能证明真实模型会选对工具或忠实判断。
3. 真实模型 + 固定工具材料：可观察受控材料下的选择与表达；本委托不默认授权付费调用。
4. 真实模型 + 真实服务：涉及当前数据、费用与不确定性，必须满足单独的授权和隔离条件。

缺少第 3/4 类时仍完成静态及可行的动态报告，把真实能力标为未验证并列最小补验集，
不把测试替身写好的正确输出统计成 Agent 成功率。若有真实调用授权，记录模型/配置、样本、
调用与耗时、预算及重复次数；小样本只报告观察，不推出稳定成功率。故障只定位和复现，不修理。

### 第二轮交付物与停止条件

仅新增 `docs/agent-design-inventory-report.md`，注明本轮基线、产品方向、覆盖、证据强度与未验证项。
报告应包括：

1. 与第一轮同等地位的执行摘要、设计资产地图、实际模型调用与上下文流转图。
2. 各设计领域的现状、证据、结论和盲区；区分实现错误、设计取舍、模型能力假设、缺信息与质量未知。
3. 代表性调用的脱敏输入结构与预算去向、丢失/重复信息定位；可复现命令与固定材料方法写入报告，不能只留临时路径。
4. 任务链矩阵：实体识别 → 决定是否取数 → 选择/使用工具 → 组织证据 → 延续观点 → 输出轻内容；每段标出实际能力与限制。
5. 投入/回报矩阵：保留、补全、简化、替换、待核验删除候选。分别说明用户收益、证据、设计/实现/验证/维护成本、依赖和置信度，不先写排期。
6. 与第一轮的交叉结论：哪些系统缺口影响 Agent 能力，哪些 Agent 设计要求系统支持；同时列出不值得增加复杂度的部分。
7. 真实服务最小补验条件、仍需产品决定的问题，以及明确停止点。

每个领域都有结论或未覆盖原因，关键判断可追溯到证据，结束时证明业务文件及第一轮报告未变。
不要求系统与 Agent 问题数量相等；要求审查广度、深度和证据标准同等。完成后停止，等待主线取舍。
