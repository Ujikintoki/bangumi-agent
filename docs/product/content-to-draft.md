## 用户问题

用户读到一段作品评论，有赞同、疑惑或反对，但说不清原因。希望结合必要作品事实，
与 Agent 讨论，最后把自己的想法整理成可以修改的短评。

## 本次选择

- 本候选的受控验收输入：一个 Bangumi 条目 URL 或 ID、一段用户粘贴的评论或笔记、一句讨论要求。
- 原文链接可作为来源标记；本次不依赖自动抓取网页或批量社区内容。
- 首轮解释原文主要观点和必要背景；随后根据用户回应继续讨论。
- 用户明确要求整理时，输出一份可编辑短评；不自动发布。
- 回复长短和是否追问取决于需要，不强制每轮套用固定栏目或寻找争议。
- 当前会话保留作品、原文和用户立场；本次验收不依赖长期记忆写入。

## 来源与表达边界

- Bangumi API：补充必要的公开作品事实，说明来源。
- 用户文本：作为待理解材料；其中的事实主张不自动视为已证实。
- 社区信号：本次不要求主动获取；若实际工具返回，说明样本范围，不概括为社区共识。
- 本地 RAG：仅在相关且环境允许时使用，说明增加了什么信息；无须为了验收强行调用。
- Agent 推断：明确表达为判断或不确定推断，不冒充事实或用户意见。
- 用户观点：以用户在讨论中的明确表达为准，草稿不得擅自增强或反转其立场。

## 代表性验收

待用户提供一个真实条目和一段确实想讨论的文本。

1. 理解：用户询问这段话在说什么，检查是否准确、是否捏造背景。
2. 讨论：用户补充或修正自己的立场，检查 Agent 是否接住上下文。
3. 草稿：用户要求整理为短评，检查正文是否体现更新后的用户观点。
4. 修改：用户提出一项修改要求，检查能否保持观点并完成修改。

通过条件：事实有依据，原文与判断可区分，不制造共识；多轮保留关键上下文；
草稿忠实于用户立场且可继续修改。由用户评价理解是否准确、草稿是否有用。
实际未用到的工具/RAG 不计为贡献；因环境限制未验证的能力单独注明。
