# 当前产品探索锚点

> 维护状态：已冻结，不再更新。下文保留原探索过程和候选，旧的下一步已失效；当前共识见 [PRODUCT](../../PRODUCT.md)，工作顺序见 [ROADMAP](../../ROADMAP.md)。

> 核对日期：2026-10-15。本文汇总当前仍有效的产品共识、证据、候选能力和下一步方法。
> 它不是功能 backlog，也不代表所有候选都要实现。稳定产品边界仍由 `PRODUCT.md` 负责，
> 当前执行顺序仍由 `ROADMAP.md` 负责。

## 为什么重新锚定

项目已经具备 Pipeline、ReAct、Persona、L1/L2、RAG 和 Bangumi 工具，但这些横向能力尚未被
一条真实用户链路组织成产品。最初提出的“条目 + 用户内容 → 理解 → 讨论 → 草稿”仍是合理
候选，却过早假定了固定输入和固定终点。后续讨论与公开页面抽样带来以下修正：

- 用户 message 不一定是 query，也可能是感受、补充、纠正、材料、偏好或对上一轮的回应；
- 用户可能只说一句“这集看得我难受”，当前页面和对话状态也是输入的一部分；
- 事实查询可以独立完成，也可以自然进入作品讨论；
- 草稿是用户明确提出时的可选出口，不是每段对话的必然终点；
- Bangumi 页面或 endpoint 很多，只证明存在数据和交互面，不自动证明值得做成产品功能；
- 产品希望略微更 Agent：由 Agent 理解意图、组织工具和推进过程，界面呈现上下文、依据、
  状态与待确认动作；
- “完整产品”需要观察环境、管理状态和执行动作，不能只继续增加回复能力。

## 当前定位

Bangumi Agent 是一个以自然对话为主要入口的 Bangumi 语境型共读伙伴。它结合当前页面、
用户主动提供的材料、必要的作品事实和连续对话，帮助用户查清信息、理解内容、讨论作品、
形成观点，并在用户需要时整理为可编辑内容。

它的独特位置在“浏览页面”和“参与社区”之间：Bangumi 提供作品、人物、章节、评分和社区原文；
Agent 负责理解当前情境、按需取数、区分证据与判断、延续讨论并提出下一步。

“更 Agent”不表示允许模型任意操作。当前原则是：

1. 用户不必预先找到正确功能页或写出完整指令；
2. Agent 根据上下文决定是否查询、解释、比较、追问或提出候选动作；
3. 确定性的选择、保存、删除、跳转和确认由 UI/Application 层执行；
4. 会影响 Bangumi 或外部系统的动作必须由用户明确确认；
5. 用户始终可以查看、纠正或移除 Agent 使用的上下文和状态。

## 系统真正接收的输入

真实输入不只有 `message`：

```text
当前页面或对象
+ 用户这次说的话或选择的文本
+ 当前会话状态
+ 用户主动允许使用的偏好/收藏
+ 必要的外部事实
```

一条 message 在对话里可能承担以下作用：

| 作用 | 示例 | 期望行为 |
|---|---|---|
| 查询 | “女主是谁配的？” | 查清事实，说明来源；够用就停 |
| 分享感受 | “这集看得我很难受。” | 接住感受，结合语境回应 |
| 提供材料 | 粘贴评论或只发链接 | 识别材料；信息不足时说明或追问 |
| 纠正理解 | “我讨厌的是叙事方式，不是角色。” | 更新本轮对用户观点的理解 |
| 设定边界 | “我只看到第三集，别剧透。” | 保存并遵守当前剧透范围 |
| 表达偏好 | “我喜欢克制的作品，但最近不想看太压抑的。” | 用于本轮判断；是否长期保存另行确认 |
| 延续对话 | “这个说法有意思。” | 根据上一轮自然继续，不重启任务 |
| 请求动作 | “保存这个观点”“整理成短评” | 产出候选结果或待确认动作 |

实现阶段不应因为这张表立即扩充 intent 枚举。先用真实案例确认现有分类与上下文是否真的失败。

## 能力地图：回答之外还缺什么

如果把所有界面反馈都叫“输出”，这个词会失去产品设计价值。当前按下面五种能力观察系统：

```text
观察环境 → 理解与判断 → 表达内容 → 保存状态 → 执行动作
```

| 能力 | 当前目标 | 项目现状 |
|---|---|---|
| 观察环境 | 知道当前作品、角色、章节、评论和用户选中的内容 | API 只能接收自由文本，尚无对象附件契约 |
| 理解与判断 | 查事实、读材料、比较观点、识别不确定性 | 已有 Agent 与工具骨架，真实场景尚未验收 |
| 表达内容 | 回答、解释、讨论、推荐、按需整理草稿 | 已有统一 Render，质量与多轮边界待验证 |
| 保存状态 | 保留当前对象、进度、剧透边界、用户明确立场和会话 | 有内部 session/L1/L2，用户不可见、不可直接管理 |
| 执行动作 | 打开来源、保存观点、复制草稿，以及未来经确认的站内动作 | 当前基本没有产品操作层 |

第一版不需要同时补齐五类。选定场景后，只补阻碍它通过的第一个关键缺口。

## 当前候选使用场景

以下是用来帮助用户自己设想至少三个真实场景的候选空间，不是排期。

### 页面陪看与即时理解

用户在作品、章节、角色或评论页面说“这里什么意思”“这人是谁”“这个术语怎么理解”。
Agent 使用当前对象和观看进度回答，控制剧透。

### 一句话感受进入讨论

用户说“画得这么可爱，但看着很不舒服”。Agent 不把它误判成资料查询，也不急着总结草稿；
它结合必要语境回应，并通过后续交流帮助用户说清感受来自题材、叙事还是表现方式。

### 评论阅读与观点拆解

用户选择一段短评或长评，说“我不完全同意，但不知道问题在哪”。Agent 区分原文结论、论据、
事实主张、情绪和隐含标准；用户可纠正 Agent，并形成自己的立场。

### 社区争议导航

用户问“为什么大家在吵这个”。Agent 对明确数量和范围的样本归纳分歧，区分共同事实、价值判断
和传闻，不把少量评论称为社区共识。

### 事实查询自然进入讨论

用户先问角色、声优、制作人员、评分排名或放送信息，得到准确答案后继续讨论表演、角色或作品。
事实查询既可以独立结束，也可以作为讨论的地基。

### 有依据的作品发现

用户给出感受、限制或主动选择的收藏上下文，让 Agent 给少量候选并解释差异。用户可以继续修正
条件；推荐不能只靠标签相似或假装理解完整口味。

### 辅助表达与社区参与

用户明确要求后，Agent 将本轮形成的观点整理为短评、回复、总结或提纲，并根据用户反馈修改。
Agent 不擅自增强、反转用户立场，也不自动代表用户发布。

## 基础查询的地位

用户明确认为作品、现实人物、虚构角色、评分/排名、近期热度和最近放送是基础能力。它们不是
低价值附属功能，而是 Agent 可以独立完成的任务，也是主观讨论的事实地基。口径必须分开：

- 评分排名：某种评分榜及其范围中的位置；
- 近期趋势：一定时间范围内的关注度或活跃度；
- 放送日历：计划播出日期，不等于某个平台已经更新；
- 作品/人物/角色信息：需要明确实体、关系和数据更新时间。

当前代码有相应工具资产，不代表实际 API、路由、Render 与最终答案已经通过真实请求验收。

## 产品形态偏好

产品不应变成“传统番剧管理后台附带聊天框”。更合适的关系是：

```text
自然对话是主入口
Agent 组织查询、理解、讨论和候选动作
UI 显示当前上下文、依据、状态和确认点
确定性服务执行用户确认后的动作
```

近期值得探索、且能复用现有能力的产品层包括：

1. **对象附件**：当前页面或用户选择的条目、角色、章节、评论作为显式上下文；
2. **可见状态**：当前作品、观看进度、剧透范围、所用材料和本轮目标可查看、修改、移除；
3. **依据面板**：区分 Bangumi 事实、用户原文、有限社区样本、Agent 判断和用户观点；
4. **会话工作区**：新建、命名、继续和删除讨论，必要时保存观点或草稿；
5. **候选动作**：打开来源、继续讨论、保存观点、复制草稿等由用户选择；
6. **只读收藏上下文**：用户主动选择后用于推荐、排除已看作品或控制剧透。

这些是候选能力，不等于现在开始建设完整 Web。当前先通过场景确定哪些状态和操作真的必要。

## OtakuNeko 带来的启示与边界

源码研究显示，OtakuNeko 的完整产品感主要来自普通 API 和专用 UI：对象附件、工具状态、会话、
收藏、排班和外部集成；其 Agent 工具本身主要是读取和分析。由此得到的原则是：

- 不把所有产品操作都包装成 Agent Tool；
- Agent 负责理解、组织和提出候选；确定性程序负责状态和执行；
- 优先借鉴对象附件、依据可见、会话管理和只读上下文；
- 完整收藏管理、跨平台同步、拖拽排班、日历导出和下载器会产生新的业务链路，不能顺手加入；
- 只参考产品思想并独立实现；上游许可文件在所核对提交中仍需进一步确认。

详细证据见 [`otakuneko-capability-study.md`](otakuneko-capability-study.md)。

## 内容、来源、人格与记忆边界

1. 已说出的具体作品事实必须有依据；网页评论中的事实主张不自动视为已证实。
2. 明确区分作品事实、用户提供的原文、有限社区信号、Agent 判断和用户观点。
3. 归纳社区内容时说明样本数量、页面、时间和缺口，不声称代表全站。
4. Agent 可以有品位、赞同或反驳，但不攻击用户，也不靠固定口癖制造人格。
5. 用户的临时情绪、他人信息和模型推测不能自动写入长期记忆。
6. 当前会话状态与长期偏好不同；剧透范围、当前材料等应由用户看见和修正。
7. 外部写操作由用户明确确认；近期仍不自动评分、收藏、发帖或下载。

## 当前还不知道什么

- 哪些候选场景会让真实用户持续追问或重复使用；
- 用户是否愿意提供页面上下文、收藏或观看进度；
- Bangumi 所有值得使用的公开数据、网页入口和授权接口；
- 当前工具在真实网络、真实模型与隔离数据库环境中的成功率；
- 现有 intent 是否能承载非 query message，还是需要新的状态或路由；
- 页面入口应该先做本地 Web、浏览器扩展还是之后再进入 Bangumi 页面；
- 哪些状态需要持久化，哪些只属于一次会话；
- 草稿、推荐、社区归纳和只读收藏哪一项最先产生独特价值。

这些未知项用小案例和真实运行减少，不通过提前建设完整架构来回答。

## 当前任务：产生并选择真实场景

当前由两条工作同时收敛到同一个决定：

### 用户侧

用户设想至少三个自己可能真实使用的场景。每个场景只需要回答：

```text
当时在哪个页面或情境：
为什么会开口：
第一句话可能是什么：
希望 Agent 接下来做什么：
经过两三轮后想得到什么：
什么表现会让这个体验失败：
```

不要求三条都是 query，也不要求最后产出草稿。建议至少覆盖：一句感受、阅读一段内容、基础查询
自然进入讨论；用户也可以提出完全不同的真实情境。

### 项目侧

在选择实现前，补一轮有边界的能力盘点：

1. Bangumi 官方 API、公开页面和授权能力分别提供什么；
2. 当前仓库已经接入、部分接入或尚未接入什么；
3. 每种能力可能服务哪些用户场景；
4. 数据可靠性、隐私、写入权限和实现重量；
5. 哪些只是技术可能，哪些已有用户问题或公开表达证据。

能力盘点用于防止遗漏，不产生“所有 endpoint 都要实现”的 backlog。

### 会合点

将用户的三个以上场景与能力盘点对照，按以下标准选择第一条纵向场景：

- 用户问题是否真实、具体；
- 是否体现 Bangumi 数据或社区语境的独特价值；
- 是否发挥 Agent 对模糊表达、上下文和多步工具组合的优势；
- 是否能用现有骨架完成大部分流程；
- 是否能用一次代表性多轮请求明确验收；
- 首个缺口能否用聚焦改动解决。

选定后才写正式“问题—选择—验收”卡，原样追踪当前系统，找到第一个失败点，并只围绕它制定
最小实现。一次仍只推进一条纵向场景。

## 当前明确不启动

- 完整收藏 CRUD、收藏数据库镜像和跨平台导入；
- 可视化拖拽排班、TickTick/日历体系；
- RSS、qBittorrent 或下载自动化；
- 自动评分、收藏、发帖和批量生成社区内容；
- 多页面管理后台、公众 SaaS、移动端和多个入口并行开发；
- 新人格、复杂多 Agent 编排或不可见的长期用户画像；
- 因为 endpoint 存在就建立没有场景证据的工具或表。
