# Bangumi 公开发言：候选使用场景研究

> 维护状态：定时点证据，不滚动维护；结论限于下文记录的时间和验证范围。当前范围及工作顺序见 [PRODUCT](../../PRODUCT.md) 与 [ROADMAP](../../ROADMAP.md)。

调研日期：2026-10-13。用途：为场景选择提供真实发言依据；不是需求频率统计，也不是已确认的产品规格。

## 方法与范围

读取用户指定的五个公开网页入口，按返回顺序取小规模便利样本，不翻页、不登录、不访问用户主页。
下表中的数量是本次阅读的列表项数，不是独立用户数；日志摘要不能代替全文。

| 入口 | 本次样本 | 浏览工具显示的抓取时间 |
|---|---:|---|
| [条目吐槽](https://bangumi.tv/subject/622288/comments) | 20 条短评正文 | 1 天前 |
| [条目评论](https://bangumi.tv/subject/622288/reviews) | 8 条标题和摘要 | 4 天前 |
| [条目讨论版](https://bangumi.tv/subject/622288/board) | 11 个主题标题 | 2 天前 |
| [动画日志](https://bangumi.tv/anime/blog) | 前 20 条标题和摘要，止于《魔法少女之名》 | 2 天前 |
| [茶话会](https://bangumi.tv/group/boring) | 20 个最新讨论标题 | 当天 |

合计 79 个列表项。另尝试打开 6 个详情链接，成功读取 1 个讨论串，5 个返回内部错误或缓存未命中：
条目原作差异评论、条目类型讨论，以及动画日志中的无剧透感受、剧情疑问、茶话会中的续作期待帖。
没有把失败的详情计为读过全文。可追溯的失败链接包括
[无剧透感受](https://bangumi.tv/blog/381397)、[剧情疑问](https://bangumi.tv/blog/381395)、
[续作期待](https://bangumi.tv/group/topic/472897)。

成功详情为[结局类型讨论](https://bangumi.tv/subject/topic/41190)：工具返回主帖和 5 个回复块，
楼层号并不连续，不能据此声称读完全部回复。网页是不同时间的缓存快照；本次不提供实时热度或当前全站统计。
三个入口集中于同一部带金融题材的作品，会放大专业术语和投资话题。未对其他条目、书籍、游戏等分层抽样。

## 实际观察到了什么

以下均为转述，不保存用户名、用户画像或整篇原文。

- **短评并不都是分析请求。** 有简短好恶、单集观感、OP/ED 和可爱画风反应；也有专业术语不懂、声优作品联想，以及对轻快表现与黑暗题材反差的感受。[吐槽样本](https://bangumi.tv/subject/622288/comments)
- **条目评论页混合多种写法。** 样本有分集观感、原作与动画差异说明，也有极短玩梗和偏离作品的个人经历。不能仅凭 `/reviews` 就把内容认定为可靠长评。[评论样本](https://bangumi.tv/subject/622288/reviews)
- **讨论版包含具体求助。** 标题涉及字幕选择、结局类型、动画改编进度、类型判断，也有社交邀约和个人记录。[讨论版样本](https://bangumi.tv/subject/622288/board)
- **详情显示求助与证据冲突同时存在。** 成功读取的帖子以观看顾虑开场；回复混合剧情陈述、听说和相互纠正。因此“有人这么说”不能直接变成作品事实。本研究未核实该串的剧情主张。[详情](https://bangumi.tv/subject/topic/41190)
- **跨作品日志展示较长表达。** 前 20 条中有观后感、叙事与角色评价、对其他评论的反驳、分集概括，以及无剧透的观看感受；同时也有很短的记录。这里只读取摘要，未验证作者对作品的具体断言。[动画日志样本](https://bangumi.tv/anime/blog)
- **茶话会范围明显超出作品。** 标题包含续作期待、社区使用问题、生活困扰、闲聊和公共话题。它能提供社区语气样本，却不能单独证明本产品应该承接所有这些任务。[茶话会样本](https://bangumi.tv/group/boring)

## 由观察推导的候选 message

下面全部是研究者改写的假设输入，**不是用户原话，也不是已经验证的 Agent 使用需求**。
同一条消息可以同时需要查询和讨论，不能仅按网页入口机械分类。

| 候选 message | 依据 | 预期任务与验收重点 |
|---|---|---|
| 久留美这番讲什么？先别剧透。 | 讨论版类型与观看顾虑 | 作品定位；区分简介和评价，控制剧透 |
| 女主是谁配的？她还配过哪些角色？ | 吐槽中的声优联想 | 人物关系查询；需核对角色和配音对应 |
| 第一集那些外汇词没听懂，用剧情语境解释一下。 | 吐槽中的术语困惑 | 术语解释；不能把讨论延伸成交易建议 |
| 画得这么可爱，故事却让我不舒服，你怎么看？ | 吐槽中的表现反差 | 接住感受并讨论；不强行生成草稿 |
| 第二集我觉得无聊，可有人觉得不错，可能差在哪？ | 吐槽中并存的不同评价 | 比较评价维度；不声称掌握多数意见 |
| 我只看了第一集，动画和漫画有哪些差别？ | 评论页的改编差异摘要 | 比较材料并标明可靠性；限制剧透范围 |
| 动画大概会改到原作哪里？确定了吗？ | 讨论版改编进度标题 | 区分已公布信息与预测，缺依据就承认未知 |
| 可以剧透：这作品算悲剧结局吗？回复怎么互相矛盾？ | 已读取的结局讨论详情 | 分离原作进度、传闻和推断；不照抄回复为事实 |
| 帮我看看这个页面抽到的评论，主要在夸什么、嫌什么。 | 吐槽样本 | 小样本归纳；说明页码、数量、时间与局限 |
| 这篇长评最核心的理由是什么？我觉得结论说重了。 | 动画日志中的叙事评价 | 理解与质疑论证；要有正文，摘要不足时说明 |
| 我喜欢角色，但不认同他的做法，这冲突吗？ | 动画日志中的角色评价 | 澄清评价标准；允许有立场的讨论 |
| 不剧透地说，这类压抑作品适合我现在看吗？ | 动画日志中的无剧透感受 | 结合用户偏好做观看判断；不冒充客观结论 |
| 如果能选一部出续作，你会选哪部？ | 茶话会续作期待标题 | 兴趣闲聊；没有明确条目也可以开始 |
| 把我们刚才聊的意思整理成短评，别替我把话说绝。 | 日志中的表达形态，加上现有产品假设 | 可选的辅助表达；忠实用户立场。对 Agent 代写的需求尚无直接证据 |

## 查询基础与主观任务的关系

用户明确提出的基础需求包括作品资料、现实人物与虚构角色、排名、近期或当日放送。
这些需求来自本次产品讨论，不能说是由上述 79 条发言统计出来的。
网页导航确实提供排行榜、每日放送、人物和角色入口，但本次没有逐项验证其数据接口。
用户提供的是网页路由，并不意味着存在同路径的稳定公开 API。[Bangumi 页面导航](https://bangumi.tv/subject/622288/comments)

可用于后续验收的查询输入包括：查某作品年份和制作信息、查某角色声优、限定类型和年份的排名、
今天有哪些番放送。放送日期不等于播放平台已经更新；“实时”必须另定数据来源、时区和更新时间。
排行也须明确条目类型、筛选范围与查询时间。这些是设计要求，尚未在本研究中验证现有系统能力。

配合本研究的本地静态检查发现，[客户端](../../clients/client.py)已有作品、角色、人物搜索，
以及放送、趋势和社区内容相关调用封装。此处只说明已有代码资产，不代表真实 API 或整条 Agent 链路已通过验收。
尤其应区分评分排名、近期趋势热度与每日放送表，三者不能相互替代。

建议把事实查询作为可独立完成的任务，也允许它服务于主观讨论。例如：先确认声优是谁，
再聊声音是否适合角色。纯感受闲聊无须每次查数据；复杂评价也不能只凭条目元数据作答。

## 对下一步的建议（尚未实施）

现有[内容到草稿场景卡](content-to-draft.md)仍可作为辅助表达的候选，但这批样本支持先扩大候选入口：
一句感受、一个问题、一条链接或一段原文都可能是开场。“条目 ID + 原文 + 最终草稿”不宜成为整个产品的唯一使用格式。



建议先选择三个小案例做现有能力追踪：一个事实查询、一个无需原文的作品讨论、一个带原文的理解与反驳。
它们用于比较最先该补哪里，不表示同时开发三条功能。草稿由用户明确提出时才进入。
选择其中一条作为首个实现任务后，再修订场景卡的验收输入。

这次证据证明的是社区中存在这些表达形态，并未证明用户愿意把相同问题交给 Agent、会持续使用，
或哪类场景优先级最高。后续需要看真实试用中的追问、纠正、继续讨论和结果使用情况。
