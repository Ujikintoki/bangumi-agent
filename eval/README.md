# eval/

BGM Agent 的离线评测：**什么在测、怎么跑、哪些数字能信。**

> **本文件是 eval 的唯一事实来源（"怎么跑 + 现在什么数"）。** `docs/eval/` 下 11 篇是
> 2026-07-31 ~ 08-17 的**计划书**，里面的规模与路径多数已过期（写"45 场景"实际 30、
> "4 人格"实际 3、"GPT-4 做 judge"实际只有 DeepSeek）。当"当时为什么这么想"读。

> **"数字从哪来"见 [`DATA_PROVENANCE.md`](./DATA_PROVENANCE.md)。** 那份文档逐条记录
> 每条轴的**标准答案由谁产生、检索由谁执行、两者是否独立**，以及全部已确认缺陷的证据
> 与复现命令。读任何数字之前先读它 —— 本文件只说明"这条轴在测什么"，不保证"那个数是真的"。

## 取向：工程 eval，不是学术 eval

| | 学术 eval | **本项目** |
|---|---|---|
| 问题 | 我的方法比 SOTA 好吗 | **这次改动弄坏东西了吗，5 分钟内能知道吗** |
| 要的 | 显著性、泛化性 | **密闭、便宜、可复现、可辩护** |
| 数字 | 越多越全越好 | **越少越可信** —— 每个指标都是一句要辩护的话 |

三条推论贯穿全篇：

1. **密闭性 > 覆盖度。** 会写外部状态的测试，第二次跑不是同一个实验。
2. **跑不起来的 eval 比没有 eval 更糟** —— 它是假的安全网。
3. **公开的数字必须保守。** 不可引用的历史数字单列在 [已知限制](#已知限制)。

## 快速开始

零凭据、零成本、不碰数据库，几秒出结果：

```bash
python -m eval.eval_classifier --baseline keyword
```

这是**关键词正则基线**（`_KEYWORD_RULES`），纯函数、每次跑完全一样。
它同时是轴 1 的对照锚：用来看 LLM 分类器比一条正则强多少。

要跑 LLM 分类器（需 `LLM_API_KEY`，量级 ¥0.05）：

```bash
python -m eval.eval_classifier --baseline llm
```

改完检索相关代码，想确认"没弄坏东西"（需 PostgreSQL/pgvector + `ZHIPU_API_KEY`，实测 ~40s）：

```bash
python -m eval.rag_eval --check       # I1–I8 + R1–R3；退出码 0 = PASS
```

## 轴 1 · 意图路由

```
数据  data/intent_queries_v7.json      102 条（主集，冻结）
      data/intent_adversarial.json      35 条（对抗集）
方法  有监督分类评测。LLM 是被测对象，关键词正则是对比锚。
      输入输出都是文本，不碰数据库、不碰 Bangumi API —— 这是它可信的全部原因。
指标  Macro F1（主）
      accuracy（仅作与基线对比的叙述）
      per-class 表 + 混淆矩阵（下钻用，不是主指标）
```

```bash
python -m eval.eval_classifier --baseline llm        # 主集
python -m eval.eval_classifier --baseline llm --data eval/data/intent_adversarial.json
python -m eval.eval_classifier --baseline keyword    # 基线
```

**为什么 Macro F1 而不是 accuracy**：7 类不均衡（chat 36 条 vs profile 8 条）。
只看 accuracy 的话，把 8 条 profile 全猜错也只掉 7.8 个点，看不出来。

**当前数字**（2026-09-12）：

| 运行 | 主集 | 对抗集 |
|---|---|---|
| `llm` | 90.20% / Macro F1 **0.8946** | 71.43% / 0.7355 |
| `keyword` | 71.57% / Macro F1 **0.7908** | 57.14% / 0.5473 |

> **关键词行是确定性的**（纯正则，每次跑逐位相同）—— 它是本轴唯一严格可复现的数字。
> **LLM 行有 run-to-run 漂移**（temperature > 0），判断回归时看趋势，不看单次。
> 已知的两次：2026-08-01 = 89.22% / 0.8839，2026-09-12 = 90.20% / 0.8946，
> 差 1 个点（92 vs 91 条正确）—— 但期间代码有变动，**不是纯净的噪声测量**。

## 轴 2 · RAG 检索

**要抓的失败**：该召回的条目**从没进过候选** —— 一旦没进候选，RAG 通道内无法补救。
（产品层还有 Bangumi API 兜底，所以这是质量损耗，不是致命伤。）

```
数据  data/rag_gt/ —— 34 条查询、四组，可信度完全不同（本轴最难的地方）
  A   自测      15 条  GT 与检索用【同一个 WHERE 子句】→ 四个数都是构造的
  A'  解析缺口   3 条  检索条件「从查询文本抽」vs「从 GT 反解」→ 专门量这个差
  B   精确名称   7 条  GT 是人工写死的 entity id，检索器须靠名字独立找到
  C   池化人工   9 条  候选池由被测检索器自己产生 → 偏高，仅定性
```

**两条口径，别混** —— 这是本轴最容易读错的地方：

| 口径 | 是什么 | 出现在哪 |
|---|---|---|
| **生产路径** | 线上真正跑的：先从查询文本抽过滤条件 → keyword **凑满名额就短路**，name/vector 根本不跑 | 「分组指标」表、`--check` 的 I1–I8 |
| **通道探针** | 让 keyword / name / vector **各自单跑**一遍，末列附一个本地复刻的**非短路**融合 | 「通道探针」表、`--ablate` |

探针**不是线上行为**，它的唯一用途是回答**「该修哪条通道」**：融合数字答不了这个 ——
keyword 一满员，其他通道就被挤出去，看起来像它们不存在。
**两张表不可相减归因**：探针的过滤条件来自 GT 反解，生产的来自文本抽取，
C 组干脆没有可注入的条件。

```bash
python -m eval.rag_eval --build     # 生成自动 GT + 池化标注模板（中间隔着人工标注）
python -m eval.rag_eval --evaluate  # 分组指标 + 短路分布 + 通道探针（只打印）
python -m eval.rag_eval --check     # ★ 本轴的基线：I1–I8 + 棘轮 R1–R3，PASS/FAIL + 退出码
python -m eval.rag_eval --check --no-probe             # 跳过探针 pass，省 ~35 次 embedding
python -m eval.rag_eval --check --freeze --reason "…"  # 收紧棘轮基线（只能删条目，不能加）
python -m eval.rag_eval --ablate    # 消融：以生产参数为基准，每行只动一个开关
```

### 当前数字（2026-09-13）

**分组指标 · 生产路径** —— 不报全局均值，它会把四组混成一个解释不了的数：

| 组 | #Q | Recall@5 | Precision@5 | NDCG@5 | MRR | 能当质量数字用吗 |
|---|---|---|---|---|---|---|
| A 自测 | 15 | 0.2230 | 1.0000 | 1.0000 | 1.0000 | ❌ `P/NDCG/MRR` 是构造值，`R@5` 被天花板压住 |
| A′ 解析缺口 | 3 | 0.1063 | 0.7333 | 0.7380 | 0.8333 | ❌ 量的是**解析器的差距**，不是检索器的能力 |
| B 精确名称 | 7 | **1.0000** | 0.2000 | **1.0000** | **1.0000** | ✅ 唯一有信息量的自动组 —— 但已到顶 |
| C 池化人工 | 9 | 0.3068 | 0.4222 | 0.4913 | 0.7778 | ⚠️ 池化偏差 → 偏高，仅定性 |

> B 组 `Precision@5 = 0.2` 是**假象**：GT=1 而 K=5，命中即 1/5。B 组只看 Recall/MRR/NDCG。
> A 组的 `Recall@5` 不是 1.0，但同样无信息量 —— `|GT|` 9–55 ≫ K=5，测的是 GT 定义。
> **四个数都没有信息量，但理由是两套**，混为一谈会让人以为"只要 Recall 不等于 1 就还有救"。

**短路分布**：34 条里 **23 条被 keyword 短路**（name/vector 从未被调用）。
这不是缺陷，是生产融合的成本设计 —— 但它意味着**多数查询的向量通道在本次评测中
从未被测量**，这也是消融必须跑在探针 pass 上的原因。

**通道探针 · 各通道单独跑的 Recall@5（非生产行为）**：

| 组 | #Q | keyword | name | vector | 融合（非短路复刻） |
|---|---|---|---|---|---|
| A 自测 | 15 | **0.2230** | 0.0000 | 0.0286 | 0.2230 |
| A′ 解析缺口 | 3 | 0.2397 | 0.0000 | 0.0279 | 0.2397 |
| B 精确名称 | 7 | 0.0000 | **1.0000** | 0.8571 | 1.0000 |
| C 池化人工 | 9 | — | 0.0000 | **0.3830** | 0.3691 ⚠️ |

> C 组的 `keyword` 是**没跑**，不是"跑了没找到" —— 池化查询没有可从 GT SQL 反解的条件可注入。
> C 组融合（0.3691）**低于** vector 单独（0.3830）：name 通道在语义查询上返回不相关结果，
> 却因优先级更高，把 vector 的相关结果挤出了前 10。**只看融合数字，这个损失不可见** ——
> 这正是通道探针存在的理由。

**三条通道各管一类查询，几乎不重叠**：keyword → A/A′、name → B、vector → C。
「融合分低」和「通道能力差」是两件事，修法完全不同（前者改融合顺序，后者换模型）。

**消融 · 基准 = 生产参数**（每行只动一个开关；跑在探针 pass 上，耗时 149s）：

| 配置 | Recall@5 | delta | 读法 |
|---|---|---|---|
| `baseline (生产参数)` | 0.4231 | — | 线上跑的那套参数 |
| `-threshold` | 0.4231 | ±0.0000 | 阈值只丢弃距离 > 0.65 的候选；baseline 是纯距离排序，丢尾部只能让列表变短、改不了顺序 ⇒ **前 10 名本来就都在 0.65 以内**，阈值从未成为限制 |
| `+bucketing` | 0.4132 | **−0.0099** | **不该在生产开分桶**（C 组 −0.0374） |
| `-mmr` | 0.4231 | ±0.0000 | 本代码里 MMR = **同名去重**（按 `name_cn or name`）。域限定到 `subject_type=2` 后，跨媒体同名副本进不了候选池 → 无重复可去 |
| `vanilla (全关)` | 0.4231 | ±0.0000 | **必然**与 baseline 相同：三个开关里 threshold / mmr 本就无作用，bucketing 在 baseline 里本就是关的 —— 这一行不是表坏了 |

> 消融**必须**跑在探针 pass 上：生产 pass 里 23/34 条被短路，向量通道根本没跑，
> 在那里做消融，整张表会几乎全平。那不是"组件没用"，是"组件没跑"。
> 代价：这张表的 baseline 行 =「向量通道单独跑」，**不等于线上表现**。

### 本轴的基线是断言，不是分数：I1–I8 + R1–R3

**本轴没有质量基线，而且不该有。** A 组的分数是构造的、B 组到顶了（1.0）、
A′ 量的是解析差、C 组有池化偏差 —— 冻结这四个里的任何一个，冻的都是一个解释不了的东西。

所以本轴交付的是**不变量**：一条可辩护的结构性质。它成立时不说明系统好，
**破掉时一定说明系统坏了** —— 这恰好就是"这次改动弄坏了没有"。

**8 条硬不变量**（违反即 FAIL）：

| # | 不变量 | 保的是哪一层 | 破掉说明什么 |
|---|---|---|---|
| I1 | 关键词通道形状契约（阶段 2 补齐不越界、不截断） | 检索层 | SQL 过滤 / 融合截断 / 实体过滤坏了 |
| I2 | A 组自测回环（stage1 精确命中） | 检索层 | keyword 通道退化 |
| I3 | 短路契约（生产融合的成本特征） | 融合层 | 短路条件变了 → 成本 / 延迟特征变了 |
| I4 | B 组精确名称排第一（MRR = 1.0） | 检索层 | trigram 名称通道退化，或被 keyword 挤掉 |
| I5 | A 组前提成立（生产解析 ≡ GT SQL 反解） | **解析层** | A 组已不再是自测组，报告里 A 的读法要改 |
| I6 | 无查询静默返回空 | 检索层 | 最隐蔽的失败：不报错，只是"不知道" |
| I7 | GT 为空清单不变（已知只有 p07） | 标注层 | 标注被改动，该查询会从统计里静默消失 |
| I8 | 仪器健康（探活可用 ∧ 两趟 pass 无通道级失败） | **测量仪器** | **坏的是尺子不是被测对象** —— 先排网络 / 服务 |

> **I1 与 I5 保的是不同层，缺一不可。** I1 保检索层（keyword 通道本身），
> I5 保解析层（生产从查询文本抽出条件的那一步）。
>
> **I8 保的是仪器。** 通道失败若被静默吞掉，"某通道返回 0 条"就有两种无法区分的原因：
> **它真找不到**（被测对象的问题）vs **它根本没跑起来**（评测工具 / 网络的问题）。
> 没有 I8，一次 embedding 服务故障会被读成"向量通道能力差"。

**3 条棘轮**（违规集必须**恰好等于**冻结集；新增 = 缺陷，减少 = 基线可收紧。
冻结文件 `data/rag_gt/check_baseline.json`）：

| # | 棘轮 | 抓什么 |
|---|---|---|
| R1 | 解析域内支持（逐 tag 有预言机） | 解析出的标签在查询域内 `COUNT = 0` |
| R2 | 阶段 1 非空（无预言机） | 有过滤条件却命中 0 条 —— 抓「多标签 AND 为空」 |
| R3 | 解析指纹（全量 34 条） | 解析结果**发生变化** —— 抓跨字段冗余这类 R1/R2 都放行的错 |

> R1 与 R2 是**不同层**：R1 逐 tag 查库（有预言机），R2 只读通道自己的输出（无预言机）。
> R3 是**输入侧**指纹 —— 它不判断对错，只保证"解析结果不会悄悄改变"。
> 收紧基线用 `--check --freeze --reason "…"`（**只能删条目**，不能加）。

**三条设计约束**（缺任何一条，这批断言就退化成又一个 A 组）：
**手写**（不由当前运行结果自动生成）、**对库漂移免疫**（I1 当场重算 GT，灌了新数据照样成立）、
**可归因**（每条指向一个具体坏法，不是"分数跌了"）。

### 为什么本轴不出质量数字

`Recall@K` 要成立，**每条查询的 GT 必须封顶 ≤ 10**。当前不满足：topic 类查询的 GT
是"所有匹配条目"（中位 24、最大 58），而检索只返回 10 条 —— 于是 `Recall@5` 的
结构性天花板 ≈ 5/31，**测的是 GT 定义，不是检索质量**。

封顶意味着引入一个新的主观决定（"前 N 个"按什么排？）并重生成全部 GT。
**已决定不做**（判据：先问错了的代价有多大 —— RAG 是 tool，错了有 Bangumi API 兜底）。
分组报告把这个天花板**显式暴露**出来，但没有消除它。**这是取舍，不是缺口。**

**标注是人在环的**：`--build` 产出模板 → 人工逐条标 → `--evaluate`，中间可隔任意时长。
这也是本轴没有统一批处理入口的原因（见[目录结构](#目录结构)）。

## 轴 3 · 回复质量

**生成 / 判定分离**：生成（跑一次 `/chat`）贵、有抖动、要联网；判定（读一段现成回复
打勾）便宜、确定性、可离线。生成侧把结果**冻结成样本**落盘，判定侧就变成对一份死文件的
纯函数 —— 同一份样本可反复判、换 rubric 重判、事后复查，都不必再跑一次生成。
**判定侧的数字因此不随 LLM 抖动，这是本轴能出"靠谱数据"的前提。**

```
数据  results/frozen/reply_quality-<run_id>-<githash>.json
      生成侧冻结样本：回复原文 + depth/persona/intent/tools + render 信号 + settings 快照
方法  生成侧  --record   跑 /chat，冻结样本（要联网、要花钱）
      判定侧  --judge    读冻结样本算指标（离线、免费、确定性、可反复跑）
```

```bash
python -m eval.reply_quality_eval --record              # 录制（要联网、要钱）
python -m eval.reply_quality_eval --record --offline    # 只录不依赖 Bangumi API 的场景
python -m eval.reply_quality_eval --judge <frozen.json> # 判定（离线、免费、可反复跑）
python -m eval.reply_quality_eval --list                # 列出已有冻结样本
```

### ⚠️ 密闭性：本轴的硬前提，且隔离键是 `user_id` 不是 `session_id`

L2 记忆召回按 **`user_id`** 检索（`agent/memory/long_term.py` 里
`SessionMemory.user_id == user_id`），**`session_id` 压根不参与查询**。
而 e2e 场景此前一直共用 `user_id="eval"`，于是**第 N 次运行一开局就带着第 N-1 次的成绩**，
同一轮里排在前面的场景也会污染后面的。

轴 2 不受影响（纯检索，不生成文本）；但轴 3 判的就是文本 —— 带着上轮记忆生成的回复，
质量分数没法归因。**所以两个 runner 都给每个场景发一个 run-scoped 的 `user_id`**
（`eval-<run_id>-<scenario_id>`）。改这两个 runner 时，别把这一行改回固定值。

| **render 降级** | **9.5%** | 10.5% | 0.0% | render 挂了 → 有可示人原文就清理后降级，没有就回落兜底话术 |
| 超软上限 | 4.8% | 5.3% | 0.0% | 超过该人格该 depth 的建议字数 |
| 超硬截断上界 | 0.0% | 0.0% | 0.0% | 本该恒 0 —— 不是 0 说明降级路径真超了上界 |
| **格式泄漏** | **4.8%** | 5.3% | 0.0% | 明细：`prompt脚手架`×1 |

> 字数 p50=98 p95=222 max=305。软上限是 **(人格, depth)** 的函数：
> base fast 200 / deep 350，kawaii 的 fast 覆盖为 **250**
> （`_WORD_LIMIT` + `profiles.py:360` 的 `word_limit_override`）；硬截断 fast 280 / deep 480。

> ⚠️ **deep 只有 n=2**（A5、C5），"deep 报错 50%"= 1/2，样本量撑不起结论。
> `--offline` 把 9 条依赖 Bangumi API 的场景全跳了，其中包含 E 组全部 deep 讨论场景
> （E1/E2/E6）—— 而 deep 管线恰恰最可能在那里出事。**本表读 fast 列，deep 列留待联网重录。**

**不报"字数合规率"**：render 会把回复硬截到 ≤ 280/480，所以对着硬截断的合规率**恒为
100%**，报了没有信息量（这和 `graph_smoke` 里 `word_range` 上界空转是同一个坑：
场景集的上界是 300/500，都 ≥ 硬截断线）。真正有信息量的是上表那三个信号。

**泄漏类别**（判定侧的模式与 `main.py:_degrade_render_input` 的清理范围一一对应，
另加一条 `prompt脚手架`）：markdown 表格 / markdown 标题 / markdown 分隔线 / emoji /
代码围栏 / XML 工具调用 / prompt 脚手架。

> **`prompt脚手架` 这一类是本轴首次跑就抓到的真实缺陷，已修（2026-09-13）。**
>
> 现象：render 的 LLM 返回**空串**时 `render_reply` 返回 None → 调用方降级为
> `_degrade_render_input(render_input)`；而 **chat 分支的 `render_input` 本身就是
> 给模型看的指令**（`用户对你说：<原话>\n\n这是一段闲聊。自然地用你的角色性格回复。
> 不要列数据、不要提搜索、就像朋友聊天一样。`），`_degrade_render_input` 只清
> emoji/markdown、**不清脚手架** → 内部提示词原样吐给用户。样本 `B6-闲聊回应` 复现。
>
> 根因是一个变量兼两用：`render_input` 既当模型输入、又当降级素材，判断条件
> `render_input != "（无数据）"` 只能区分"有没有数据"，区分不了"能不能给人看"。
> 修复把两者拆成 `render_input` / `fallback` 两个变量，chat 分支的 `fallback` 为 None
> → 回落 `render.py:render_fallback_line()` 的角色兜底话术。
> 顺带堵住被泄漏掩盖的第二个坑：chat 分支若直接返回 None，端点会往上翻到 L1 缓存中
> **上一轮的回复**当成这一轮的回答（chat 直通 END，本轮不产生新 AIMessage）。
> 回归测试见 `test/test_render_fallback.py`。
>
> **上表是修复前的数字，`格式泄漏 4.8%` 是历史事实，不是当前状态** —— 冻结样本是死文件，
> 修完不重录它依然在。想拿到修复后的数字只有一个办法：联网重录（要花钱、要 Bangumi API）。
> 判定侧的 `prompt脚手架` 模式**保留不删**：它是这一类的回归哨兵，删了就再没人守。
>
> 同一轮 render 失败在 `D5-社区评价` 上是**按设计工作的**：那条的 `render_input` 是
> Aggregator 的可读文本，降级后是"搜索超时，未能获取…建议稍后重试"。这组对照是定位根因的
> 关键证据 —— 问题不在"降级"本身，而在 chat 分支把指令当正文。

## 方法论约定

任何一条轴都必须满足，否则数字不可引用。

### 1. 密闭性

会写数据库 / 缓存 / 外部状态的评测，必须先隔离，否则 **run N 永远比 run N-1 偏差更大** ——
它不会像温度抖动那样自己抵消，而是单向累积。

隔离手段：`MEMORY_ENABLED=False`，或独立 `user_id`。
**排查手法**：换一个全新 `user_id` 跑同一个场景，看数字是否变化。

### 2. GT 定义先于指标

"所有匹配条目"不是 GT，"用户会接受的结果"才是。GT 定义错了，指标再标准也是错的。
轴 2 的 `Recall@5` 就被这条卡住（见该轴的封顶前提）。

### 3. 报告头记 settings 快照，不只记 githash

`MEMORY_ENABLED` / 召回阈值 / 模型名 / temperature 都不在 git 里 ——
代码没变、数字也在变，githash 复现不了一次实验。

### 4. 判断一个数字能不能信，只看一件事

**它有没有隐藏状态。** 输入输出都是文本、无外部依赖的评测（轴 1）才敢直接引用。

## LLM-as-judge 的工程约束

判官是一台**测量仪器**。仪器必须校准，否则它测的是自己。
**违反任一条，judge 数字不许引用。**

| # | 约束 | 理由 |
|---|---|---|
| 1 | **必报 judge-human 一致率**（Cohen's κ 或简单一致率） | 无校准数字的 judge 数字不可解释。先在 20-30 条人工标注子上验证 |
| 2 | **二值 rubric，不打 1-5 分** | 人类与 judge 在二值/三值标度上的一致性远高于连续打分 |
| 3 | **judge ≠ 被评模型** —— 本项目当前做不到 | 只配了一个 provider（`LLM_MODEL` 单值），自偏好偏差真实存在，**必须写进报告头作为限制** |
| 4 | **盲判** | 不告诉 judge 这是哪个人格、哪个版本、正序还是倒序 |
| 5 | **成本守卫** | Tier 1 格式合规挂了 → 不必跑 judge。格式都不对，内容不用评 |
| 6 | **只测内容才重要的场景** | 不是全部场景都值得 judge |

**人格可区分度**（可选）：三人格盲猜，随机基线 **33%**（3 选 1）。
