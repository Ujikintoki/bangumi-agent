# eval/

BGM Agent 的离线评测：**什么在测、怎么跑、哪些数字能信。**

> **本文件是 eval 的唯一事实来源（"怎么跑"）。** `docs/eval/` 下 11 篇是 2026-07-31 ~ 08-17 的
> **计划书**，里面的规模与路径多数已过期（写"45 场景"实际 30、"4 人格"实际 3、
> "GPT-4 做 judge"实际只有 DeepSeek）。当"当时为什么这么想"读。

> **"数字从哪来"见 [`DATA_PROVENANCE.md`](./DATA_PROVENANCE.md)。** 那份文档逐条记录
> 每条轴的**标准答案由谁产生、检索由谁执行、两者是否独立**，以及全部已确认缺陷的证据与复现命令。
> 读任何数字之前先读它 —— 本文件只说明"这条轴在测什么"，不保证"那个数是真的"。

## 取向：工程 eval，不是学术 eval

| | 学术 eval | **本项目** |
|---|---|---|
| 问题 | 我的方法比 SOTA 好吗 | **这次改动弄坏东西了吗，5 分钟内能知道吗** |
| 要的 | 显著性、泛化性 | **密闭、便宜、可复现、可辩护** |
| 数字 | 越多越全越好 | **越少越可信** —— 每个指标都是一句要辩护的话 |

三条推论贯穿全篇：

1. **密闭性 > 覆盖度。** 会写外部状态的测试，第二次跑不是同一个实验。
2. **跑不起来的 eval 比没有 eval 更糟** —— 它是假的安全网。
3. **公开的数字必须保守。** 不可引用的历史数字单列在 [已知限制](#已知限制)。

## 快速开始

零凭据、零成本、不碰数据库，几秒出结果：

```bash
python -m eval.eval_classifier --baseline keyword
```

这是**关键词正则基线**（`_KEYWORD_RULES`），纯函数、每次跑完全一样。
它同时是轴 1 的对照锚：用来看 LLM 分类器比一条正则强多少。

要跑 LLM 分类器（需 `LLM_API_KEY`，约 ¥0.05）：

```bash
python -m eval.eval_classifier --baseline llm
```

改完检索相关代码想确认"没弄坏东西"（需 PostgreSQL + `ZHIPU_API_KEY`，~40s）：

```bash
python -m eval.rag_eval --check       # 6 条回归不变量，退出码 0 = PASS
```

## 评测什么

四条轴 + 一道门禁。纳入标准只有一条：**改动频率 × 坏掉代价 × 测起来便不便宜**。

| # | 评测对象 | 要抓的失败 | 主指标 | 对照基线 | 状态 |
|---|---|---|---|---|---|
| 1 | **意图路由** | 话被送进错的管线 → 调错工具、慢、答非所问 | **Macro F1** | 关键词正则 | ✅ 有数字 |
| 2 | **RAG 检索** | 该召回的**从没进过候选** —— RAG 通道内无法补救<br>（产品层有 API 兜底，见下方说明） | **回归不变量**（6 条，`--check`）<br>Recall@5（分组，仅供参考） | 不变量本身<br>生产配置（`--ablate`） | ✅ 有回归基线<br>⚠️ 无质量基线 |
| 3 | **回复质量** | 字数超标 / 格式泄漏 / 内容空洞或跑题 | **格式合规率**（免费层）<br>**rubric 通过率**（judge 层） | 硬截断兜底<br>judge-human 一致率 | ⬜ 待建 |
| 4 | **记忆** | 说过的事忘了 | **事实保持率**（固定轮距） | L2 关闭（A/B） | ⬜ 待建 |
| — | **图接线门禁** | **接线断了**（P2 子图消息复制、P3 prompt 塌缩这类零件之间的 bug） | **PASS / FAIL** | — | ⚠️ 需瘦身 |

**为什么不是十条**：每条轴都要长期维护、要被辩护。四个能持续跑的轴 > 十个跑不动的轴。
**不做的范围**：安全与隐私（只读 agent，风险面小）、工具轨迹质量（并入轴 1，与意图是同一次决策的两个出口）、
成本与延迟（并入各轴报告的副产品，不单独成轴）。

## 轴 1 · 意图路由

```
数据  data/intent_queries_v7.json      102 条（主集，冻结）
      data/intent_adversarial.json      35 条（对抗集）
方法  有监督分类评测。LLM 是被测对象，关键词正则是对比锚。
      输入输出都是文本，不碰数据库、不碰 Bangumi API —— 这是它可信的全部原因。
指标  Macro F1（主）
      accuracy（仅作与基线对比的叙述）
      per-class 表 + 混淆矩阵（下钻用，不是主指标）
```

```bash
python -m eval.eval_classifier --baseline llm        # 主集
python -m eval.eval_classifier --baseline llm --data eval/data/intent_adversarial.json
python -m eval.eval_classifier --baseline keyword    # 基线
```

**为什么 Macro F1 而不是 accuracy**：7 类不均衡（chat 36 条 vs profile 8 条）。
只看 accuracy 的话，把 8 条 profile 全猜错也只掉 7.8 个点，看不出来。

**当前数字**（2026-09-12）：

| 运行 | 主集 | 对抗集 |
|---|---|---|
| `llm` | 90.20% / Macro F1 **0.8946** | 71.43% / 0.7355 |
| `keyword` | 71.57% / Macro F1 **0.7908** | 57.14% / 0.5473 |

> **关键词行是确定性的**（纯正则，每次跑逐位相同）—— 它是本轴唯一严格可复现的数字。
> **LLM 行有 run-to-run 漂移**（temperature > 0），判断回归时看趋势，不看单次。
> 已知的两次：2026-08-01 = 89.22% / 0.8839，2026-09-12 = 90.20% / 0.8946，
> 差 1 个点（92 vs 91 条正确）—— 但期间含 P4 修复，**不是纯净的噪声测量**。

## 轴 2 · RAG 检索

```
数据  data/rag_gt/  —— 三类查询、三种可信度（本轴最难的地方）
  AUTO    25 条   GT 由 SQL 从数据库元数据直接算出（tag/year/score/career/exact）
                  ⚠ 其中 18 条（tag/year/score/career）的 GT 与检索用【同一个
                    WHERE 子句】→ 见下面 A 组
  POOLED  10 条   池化标注：多路检索结果取并集 → 人工标 relevant: true/false
                  语义查询唯一可行的办法（IR 界标准做法，TREC 同款）
方法  三件事，用途不同，别混：
        --evaluate  算指标。报告按【可信度分组】，不报全局均值（全局那个数
                    会掩盖全部差异）：
                      A 自测 18 条  GT 与检索同源 → 返回的每条必然在 GT 里，
                                   P/NDCG/MRR 恒 1.0；R@5 低是 |GT|≫K 压的。
                                   四个数【都无信息量】
                      B 质量  7 条  精确名称：GT 是人工指定的 id，检索器须靠
                                   名字独立找到 → 唯一有信息量的自动组 ★
                      C 人工  9 条  池化偏差 → 偏高，仅定性
                    另按【检索通道】分层：keyword / name / vector 各自【单独】
                    找得到多少 —— 融合数字答不了这个，keyword 一占满名额，
                    其他通道就被挤出去。
        --ablate    消融。以【生产配置】为基准，每行只动一个开关：-threshold /
                    +bucketing / -mmr / vanilla。`+bucketing` = 候选改动，
                    其余 = 关掉生产开着的东西。
        --check     ★ 本轴的【基线】。6 条回归不变量，PASS/FAIL + 退出码。
                    见下面「基线不是分数」。
```

```bash
python -m eval.rag_eval --build      # 生成 GT + 标注模板
                                     # → 人工标注 data/rag_gt/pooled_annotate.json
python -m eval.rag_eval --evaluate   # 算指标（分组 + 通道分层报告）
python -m eval.rag_eval --check      # 回归不变量（改完代码跑这个，退出码 0/1）
python -m eval.rag_eval --ablate     # 消融实验（同样分组）
```

### 当前数字（2026-09-12，生产配置）

分组指标 —— **三组可信度不同，不要平均成一个数**：

| 组 | #Q | Recall@5 | Precision@5 | NDCG@5 | MRR | 能当质量数字用吗 |
|---|---|---|---|---|---|---|
| A 自测 | 18 | 0.2258 | 1.0000 | 1.0000 | 1.0000 | ❌ 四个数都是构造出来的 |
| B 质量 | 7 | **1.0000** | 0.2000 | **1.0000** | **1.0000** | ✅ 唯一有信息量的自动组（但已到顶） |
| C 人工 | 9 | 0.3468 | 0.4667 | 0.4641 | 0.6296 | ⚠️ 池化偏差，仅定性 |
| ALL | 34 | 0.4172 | 0.6941 | 0.8582 | 0.9020 | ⚠️ 含 A 组构造值，仅供参考 |

> B 组 `Precision@5 = 0.2` 是**假象**：GT=1 而 K=5，命中即 1/5。B 组只看 Recall/MRR/NDCG。

通道分层 —— 每个通道**单独**检索时的 Recall@5（不是它给融合结果贡献了几条）：

| 组 | keyword | name | vector | 融合 |
|---|---|---|---|---|
| A 自测 (18) | **0.2258**（18/18 非零） | 0.0000（0/18） | 0.0285（**8/18 非零**） | 0.2258 |
| B 质量 (7) | 0.0000 | **1.0000**（7/7） | 0.8571（6/7） | 1.0000 |
| C 人工 (9) | 0.0000 | 0.0000 | **0.3607**（9/9） | 0.3468 ⚠️ 低于 vector 单独 |

**三条通道各管一类查询，几乎不重叠**：keyword → A 组、name → B 组、vector → C 组。

两条只看融合数字永远发现不了的结论：

1. **A 组的向量通道不是"找不到"，是"挤不进去"。** 它单独能命中 8/18 条查询
   （最高单条 R@5 = 0.1042），却在 A 组融合出的 180 条里只贡献了
   `keyword 179 + vector 1 + name 0` 里的那 1 条 —— keyword 先把 10 个名额占满了。
   **「融合分低」和「通道能力差」是两件事，修法完全不同。**
2. **C 组融合后反而更差**（0.3468 < vector 单独 0.3607）：name 通道在语义查询上
   命中 0/9，却因为优先级更高，把 vector 的相关结果挤出了前 10。
   这是"分层"最直接的一次收益 —— 只看融合分会得出"融合没问题"的反结论。

消融（基准 = 生产配置）：

| 配置 | Recall@5 | delta | 读法 |
|---|---|---|---|
| `baseline (生产配置)` | 0.4172 | — | 线上跑的那套 |
| `-threshold` | 0.4172 | ±0.0000 | `enable_threshold` 在这份数据上**完全无效**（未解释） |
| `+bucketing` | 0.4103 | −0.0069 | **不该在生产开分桶**（C 组 −0.0262，是全局的 3.8 倍 = 被 A 组稀释） |
| `-mmr` | 0.4143 | −0.0029 | MMR 有微小正向贡献 |
| `vanilla (全关)` | 0.4143 | −0.0029 | 与 `-mmr` 同值：threshold 开关无效所致 |

### 基线不是分数：6 条不变量（`--check`）

**本轴没有质量基线，而且不该有。** A 组的分数是构造的、B 组的到顶了（1.0）、
C 组有池化偏差 —— 冻结这三个里的任何一个，冻的都是一个解释不了的东西。

所以本轴交付的不是分数，而是**不变量**：一条可辩护的结构性质。
它成立时不说明系统好，**破掉时一定说明系统坏了** —— 这恰好就是
"这次改动弄坏了没有"。

| # | 不变量 | 保的是哪一层 | 破掉说明什么 |
|---|---|---|---|
| I1 | A 组 keyword 通道填满名额（返回 = `min(\|GT\|, 10)`） | **检索层** | SQL 过滤 / 融合截断 / 实体过滤坏了 |
| I2 | B 组精确名称排第一（MRR = 1.0） | 检索层 | trigram 名称通道退化 |
| I3 | 无查询静默返回空 | 检索层 | 最隐蔽的失败：不报错，只是"不知道" |
| I4 | GT 为空清单不变（只有 p07） | 标注层 | 标注被改动，该查询会从统计里静默消失 |
| I5 | 生产关键词解析不产出坏标签 | **解析层** | `acd99a4` 那个 bug 复发 |
| I6 | 本次运行无通道级失败 | **测量仪器** | embedding 服务挂了 —— 此时任何数字都不可读 |

> ⚠️ **I1 和 I5 保的是不同层，缺一不可。** A 组检索用的 `keyword_filters` 是 eval
> 自己从 GT SQL 里抠出来的 WHERE，它**绕过**了生产真正跑的
> `tools/bgm_tools.py:_extract_keyword_filters`。所以哪怕生产解析全坏，I1 照样
> 满分 —— I1 保检索层，I5 保解析层（直接调生产函数，只走规则兜底，不碰 LLM）。
>
> I5 用 DB 里的**真词表**；单测 `test/test_tools.py::TestTagVocabularyFallback`
> 用 17 个**假标签**。真词表几千个标签里的碰撞组合假词表测不出来 —— 实测 I5
> 找出了人工 sweep 没枚举到的碰撞（`孤独摇滚 → 孤独/摇滚`、`2023年 → 2023/02`）。
> 两者不重复。

> ⚠️ **I6 保的是"仪器"，不是"被测对象"。** 通道失败原来是 `except: pass` 静默的，
> 于是"某通道返回 0 条"有两种无法区分的原因：**它真找不到**（被测对象的问题）
> vs **它根本没跑起来**（评测工具/网络的问题）。2026-09-12 实测撞到：智谱 API
> 连接失败 → vector 静默归零。
>
> **把 embedding 服务整个打断后重跑**（`hybrid_search` 一律抛异常），实测结果：
>
> ```
> I1 A 组 keyword 填满   18/18  PASS   ← A 组融合 R@5 = 0.2258，与健康时【逐位相同】
> I2 B 组精确名称第一      7/7  PASS   ← B 组融合 R@5 = 1.0000，同样逐位相同
> I3 无查询静默返回空    26/34  FAIL   ← 8 条 C 组查询塌空（p02 靠 name 通道活着）
> I6 无通道级失败         34 次  FAIL   ← 唯一说得出"为什么"的一条
> C 组 R@5: 0.3468 → 0.0000
> ```
>
> **I1/I2 全 PASS** —— 一次彻底的服务故障，在这两条最像"质量指标"的断言上
> 完全看不出来（keyword/name 把名额填满了，融合数字一个字不变）。
> I3 抓到了 C 组塌空，但它只能说"空了"，说不出是"找不到"还是"没跑起来"；
> **区分这两者的是 I6**。没有 I6，一次 embedding 故障会被读成"向量通道能力差"。

三条设计约束（缺任何一条，这批断言就退化成又一个 A 组）：**手写**（不由当前
运行结果自动生成）、**对库漂移免疫**（I1 当场重算 GT，灌了新数据照样成立）、
**可归因**（每条指向一个具体坏法，不是"分数跌了"）。

**标注是人在环的**：`--build` 产出模板 → 人工逐条标 → `--evaluate`，中间可隔任意时长。
这也是本轴没有统一批处理入口的原因（见[目录结构](#目录结构)）。

### ⚠️ 为什么出不了质量数字

**使用前提：每条查询的 GT 必须封顶 ≤ 10**（当前不满足，见[已知限制](#已知限制)）。
原因：GT 若是"所有匹配条目"（中位 24、最大 58 条），而检索只返回 10 条，则
`Recall@5` 的结构性天花板 = 5/31 = 0.16 —— **测的是 GT 定义，不是检索质量**。
修法：topic 类查询（tag）的 GT 取"前 10 个用户会接受的结果"（如按收藏数）。
known-item 查询（GT=1）不受影响 —— 封顶后 Recall@5 对两类查询都成立，
这是它能当唯一指标的前提。

分组报告把这个天花板**显式暴露出来**（A 组 R@5 = 0.2258 就是这么来的），
但**没有消除它** —— B 组（GT=1）不受影响，C 组（GT 4–16）仍受影响。
**GT 封顶已于 2026-09-12 决定不做**（见 [DATA_PROVENANCE §7-D](DATA_PROVENANCE.md)）。

### 本轴做过的实验（精简）

| 实验 | 结论 | 落到哪 |
|---|---|---|
| A/B/C 分组报告 | 同源问题从均值里拆出来；全局均值掩盖全部差异 | `--evaluate` 报告结构 |
| 通道分层 | 三条通道各管一类查询；A 组向量贡献 ≈ 0 首次可见 | `--evaluate` 报告结构 |

| 回归不变量 `--check` | 本轴的基线：分数出不了，但"坏没坏"能答 | `--check`（6 条） |

## 轴 3 · 回复质量

两层，**便宜的先跑，贵的按需跑**：

```
Tier 1  确定性（¥0，每次跑）
        字数是否 ≤ 上界 / 是否泄漏 markdown 表格或 emoji / 空回复
        → 指标: 格式合规率
        → 注意: render.py 有硬截断（fast 280 / deep 480），所以字数必须
                对着 _HARD_CUTOFF_MAX_CHARS 测，不是对着 prompt 建议的 200/350

Tier 2  LLM-as-judge（按需跑，要钱）
        → 指标: rubric 通过率
        → 硬约束见 LLM-as-judge 的工程约束 —— 不满足约束的 judge 数字不许引用
```

**为什么必须是两层**：Tier 1 免费且确定性，可以挂在每次改动上；Tier 2 贵且有 judge 噪声，
只在内容真的重要的场景跑（立场评价、deep 讨论这类）。**格式都不对时不必跑内容评测**——
这是成本守卫，也是 Tier 1 存在的第二个理由。

**Tier 2 的 rubric 设计**：3 条二值 rubric，不用 1-5 连续打分。
例："是否给出了明确立场" / "是否引用了具体数据" / "是否符合该人格设定"。
通过率即主指标。

## 轴 4 · 记忆

```
方法  种事实 → 隔 N 轮 → 问回来 → 断言出现（不引入 judge，全程确定性）
指标  事实保持率（"10 个事实，隔 10 轮后仍召回 8 个"）
对照  L2 关闭（A/B）—— 直接回答"这个子系统值不值它的成本"
```

> 同款手法已有先例：人格两层的消融实验发现"管线 43x 成本无对应收益"，
> 是本项目性价比最高的一次测量。**每个子系统都该被问一次这个问题。**

## 门禁 · 图接线冒烟

```
规模  5-8 条（当前 30 条，待缩减）
选法  每条对应一个历史上的真实 bug，而非"覆盖 A-E 五维度"。
      场景的 notes 字段直接写明它守的是哪个回归，例如：
        A1-常识日期      "P0#3 回归：常识问题不得进 realtime、不得调工具"
        C5-deep必调工具  "P0#2 回归：deep 模式必须调工具"
        A4-列表格式      "markdown 表格泄漏检测（降级清理器存在的根因场景）"
        C4-找相似        "相似推荐需先搜到源作品"
产出  PASS / FAIL（不是通过率 —— 5 条场景的比率没有统计意义）
```

```bash
python -m eval.graph_smoke            # 需 DB + LLM + 真实 Bangumi API，约 1 分钟
python -m eval.graph_smoke --smoke 3  # 只跑前 N 条（联调用）
```

**它为什么不可替代**：P2（子图退还输入致消息翻倍）、P3（prompt 每轮塌缩）这类
**接线 bug**，离线分类器测试永远抓不到 —— 坏的是零件之间的连接，不是零件。

**它为什么必须瘦身**：30 条版烧 ~¥0.37 + ~6 分钟（p50 12s × 30）+ 真实 Bangumi API，
却给出一个没有统计意义的百分率。同一个 commit 相隔 7 分钟跑两次（15:13 / 15:20）：

```
16/30 → 19/30          净 +3
但状态真正翻转的有 11 条：7 条失败→通过，4 条通过→失败
```

**11 条翻转、净 +3** —— 这个比率测的是抖动，不是质量。它测到的东西几乎都能在
轴 1/3 里以 1/10 的成本、密闭地测到。

## 方法论约定

任何一条轴都必须满足，否则数字不可引用。

### 1. 密闭性

会写数据库 / 缓存 / 外部状态的评测，必须先隔离，否则 **run N 永远比 run N-1 偏差更大** ——
它不会像温度抖动那样自己抵消，而是单向累积。

隔离手段：`MEMORY_ENABLED=False`，或独立 `user_id`。
**排查手法**：换一个全新 `user_id` 跑同一个场景，看数字是否变化。

### 2. GT 定义先于指标

"所有匹配条目"不是 GT，"用户会接受的结果"才是。GT 定义错了，指标再标准也是错的。
轴 2 的 `Recall@5` 就被这条卡住（见该轴的封顶前提）。

### 3. 报告头记 settings 快照，不只记 githash

`MEMORY_ENABLED` / 召回阈值 / 模型名 / temperature 都不在 git 里 ——
代码没变、数字也在变，githash 复现不了一次实验。

### 4. 判断一个数字能不能信，只看一件事

**它有没有隐藏状态。** 输入输出都是文本、无外部依赖的评测（轴 1）才敢直接引用。

## LLM-as-judge 的工程约束

判官是一台**测量仪器**。仪器必须校准，否则它测的是自己。
**违反任一条，judge 数字不许引用。**

| # | 约束 | 理由 |
|---|---|---|
| 1 | **必报 judge-human 一致率**（Cohen's κ 或简单一致率） | 无校准数字的 judge 数字不可解释。先在 20-30 条人工标注子上验证 |
| 2 | **二值 rubric，不打 1-5 分** | 人类与 judge 在二值/三值标度上的一致性远高于连续打分 |
| 3 | **judge ≠ 被评模型** —— 本项目当前做不到 | 只配了一个 provider（`LLM_MODEL` 单值），自偏好偏差真实存在，**必须写进报告头作为限制** |
| 4 | **盲判** | 不告诉 judge 这是哪个人格、哪个版本、正序还是倒序 |
| 5 | **成本守卫** | Tier 1 格式合规挂了 → 不必跑 judge。格式都不对，内容不用评 |
| 6 | **只测内容才重要的场景** | 不是全部场景都值得 judge |

**人格可区分度**（可选）：三人格盲猜，随机基线 **33%**（3 选 1）。

## 新增一条评测

1. 在 `eval/` 下建 `<name>_eval.py`，**独立可跑**：`python -m eval.<name>_eval`
2. 复用 `metrics.py` 里的纯函数；不够用就往里加（它是唯一共享构件）
3. 数据放 `data/`，带 `version` + `created` 字段
4. 报告写进 `results/`，**报告头带 settings 快照**
5. 在本文件的「评测什么」表里加一行，并写清：要抓的失败 / 主指标 / 对照基线

**一条轴只选一个主指标。** 想加第二个指标时先问：它能不能被第一个覆盖？
不能的话，它是另一个轴，还是这一条轴该换指标？

### 未修的问题（按影响排序）

1. ~~**轴 2 的 auto 组在测自己**~~ —— **2026-09-12 已在报告层修掉**：18 条改为
   A 自测组、与 B/C 组分开呈现，并新增**通道分层**。修复后实测：这 18 条的融合结果
   180 条里 keyword 179 + vector 1 + name 0，**向量通道贡献 ≈ 0 首次可见**。

2. **GT 无上限** —— topic 类 GT 中位 24 / 最大 58，而检索只返回 10，
   使 `Recall@5` 测的是 GT 定义而非检索质量。**这条没修，且已决定不做**

   没有消除它 —— 所以轴 2 出不了**质量**数字。它的基线改由 `--check`
   的 6 条不变量提供（见轴 2 的「基线不是分数」）。
3. **`enable_threshold` 开关零效果** —— 消融里 `-threshold` 与 baseline 逐位相同
   （delta ±0.0000），未能解释。可能是这份数据里向量结果本就全落在阈值内，
   但**没有验证**，所以不下结论。
4. **门禁不密闭** —— `graph_smoke.py` 硬编码 `user_id="eval"`，而
   `agent/memory/long_term.py` 只有 `user_id == "anonymous"` 一道闸（无 run / 时间隔离），
   上一轮跑的记忆会被下一轮召回。库里已有 29 行历史污染。
5. **门禁的 `word_range` 断言空转** —— 场景声明上界 300/500，render 硬截 280/480，够不到。

### 结构性限制

- **judge 与被评模型同源**：项目只配了一个 provider，自偏好偏差无法消除，只能声明。
- **轴 2 有回归基线、没有质量基线**：`--check` 的 6 条不变量能回答"这次改动弄坏了
  没有"，但本轴**产不出可引用的分数** —— 原因见轴 2 的「为什么出不了质量数字」。
  这不是缺口，是取舍：GT 封顶 / 池化重标都已在 2026-09-12 决定不做，
  理由是投入产出不成比例（判据：**先问错了的代价有多大** —— RAG 是 tool，
  错了有 Bangumi API 兜底）。
- **轴 4 尚未产出基线**：脚本还没建。这是它目前最大的短板。
