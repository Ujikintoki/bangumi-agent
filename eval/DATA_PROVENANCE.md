> "怎么跑"见 [`README.md`](./README.md)；这份只管"数据出处"。

> 建立于 2026-09-12，起因：RAG 评测报告里出现大片 `P@5 = 1.000 / MRR = 1.000 / NDCG@5 = 1.000`，
> 追查后发现这些数字不是测出来的。**追查过程与证据全部记录在本文，不依赖任何人复述。**
>
> **修订 2026-09-12（同日晚）**：§7 的 A 类三项已实施并重跑，结果见 §9。B/C 类未动。

## 1. 核心难点：搜索的"标准答案"从哪来

分类器（轴 1）没有这个问题。"你好"该分到 `chat` —— 这是**产品定义**，写下来就是标准答案。

搜索不一样。问：「**关于音乐乐队的百合动画**」的正确答案是哪些作品？

- 库里有 1500 部作品
- 没有任何一列叫「是不是关于音乐乐队的百合动画」
- 谁也不知道答案 —— 除非把 1500 部挨个看一遍

**"标准答案"不能凭空产生。这是搜索评测全部复杂性的来源。**

于是只能走两条路，这就是"两个组"的由来 —— 不是术语，是被逼出来的分类：

| 组 | 判据 | 条数 |
|---|---|---|
| **auto** | 答案能从数据库某个字段直接查出来 | 25 |
| **human** | 答案不在任何字段里，只能人来判 | 10 |

## 2. auto 组：抄答案

### 2.1 设计意图

「芳文社」—— 每条作品都有 `tags` 字段，有些写着 `芳文社`。所以：

```sql
SELECT id FROM rag_entities WHERE tags @> 芳文社   → 31 条
```

31 条就是客观、完整、零成本的标准答案。**这个设计本身是对的。**

### 2.2 实际发生了什么

```
第一步  造标准答案 :  WHERE tags @> 芳文社                     → 31 条
第二步  拆条件     :  _parse_keyword_filters() 正则抠出「芳文社」
第三步  "检索"     :  WHERE tags @> 芳文社 ORDER BY popularity → 10 条
                      └────────── 与第一步同一个 WHERE ──────────┘
第四步  对比算分   :  P@5 = 5/5 = 1.000     ← 报告上的数字
                      MRR = 1.0            ← 报告上的数字
                      NDCG@5 = 1.0         ← 报告上的数字
```

**第一步和第三步是同一个条件。**「检索」就是「标准答案查询」加了个 `ORDER BY`。

用图书馆打比方：

> 题目：「说出 31 部芳文社的作品」
> **正常**：你进馆自己找 10 部 → 跟标准答案一对 → 找到 5 部 → 得分 5/31
> **现在**：老师拿答案单进馆抄了 10 部 → 再跟答案单一对 → **全对！满分！**

### 2.3 为什么不只是"数字虚高"，而是"零信息量"

19 条候选里 18 条走这条路（tag 12 + year 2 + score 1 + career 3）。

关键在于 `_run_retrieval()` 的融合顺序是 **keyword 优先**：

```python
merged = list(keyword_ids)        # rag_eval.py:411 —— keyword 先占满
for nid in name_ids: ...          # 再补 name
for vid in vector_ids: ...        # 最后补 vector
return merged[:limit]             # limit=10
```

`_run_keyword_search(limit=10)` 实测返回**恰好 10 条**。所以 `merged[:10]` 完全由 keyword 通道决定 ——

> **向量通道在这 18 条查询上贡献 0 条。**
> **即使向量检索彻底坏掉，这 18 条的数字一个都不会变。**

这不是"测了个没价值的东西"，是"测了个永不会失败的断言"。而它**同时掩盖**了真正想知道的事：语义检索能不能理解「芳文社」这种专有名词。

### 2.4 证据（可复现）

```bash
.venv/bin/python -c "
from eval.rag_queries import AUTO_QUERY_DEFS
from eval.rag_eval import _parse_keyword_filters, _run_keyword_search
qid,qtext,et,st,cat,sql = AUTO_QUERY_DEFS[0]
f = _parse_keyword_filters(sql)
print('抠出的条件:', f)
ret = _run_keyword_search(entity_type=et, subject_type=st, limit=10, **f)
print('检索返回:', len(ret), '条')
"
# → 抠出的条件: {'required_tags': ['芳文社']}
# → 检索返回: 10 条   （= limit，占满全部名额）
```

### 2.5 附带缺陷：GT 含 nsfw，检索器被禁止返回

| | WHERE 子句 |
|---|---|
| GT 生成 SQL | `entity_type='subject' AND subject_type=2` |
| `_run_keyword_search:140` | 上述 **+ `nsfw == False`** |

实测 **a18「动画制作人」的 58 条 GT 里有 10 条是 `nsfw = true`** —— 检索器被明令禁止返回它们，却被算进 Recall 的分母。

> **已修（§9-A2）**：GT 的 SQL 现在追加 `AND nsfw = false`，与检索范围对齐。a18 的 GT 由 58 → 48。

## 3. human 组：自己出考卷

### 3.1 设计意图

「关于音乐乐队的百合动画」—— 库里没这个字段。只能把候选摆出来，**人一个个判**。

### 3.2 候选池是被测系统自己产生的

```python
# rag_eval.py:223  build_pooled_template()
results = retriever.hybrid_search(query=qtext, ..., limit=15)   # ← 被测的检索器
```

> 想知道你找东西行不行。
> 方法是：**让你自己**先写下你能想到的 20 样东西。
> 然后检查：这 20 样里有多少是真正需要的？

**你想不到的，根本没进这张纸**，也就永远不会被发现"漏了"。

这是标准的**池化偏差**（pooling bias）。经典 TREC 的做法是**多个不同系统各跑一遍、取并集**当候选池 —— 一个系统漏的，别的系统还能捞出来。这里只有一个系统，所以：

> 凡是检索器捞不出来的，自动从考卷上消失 → 分数天生偏高。

### 3.3 另一条：GT 大小被池子大小封顶

human 组 GT 为 4–16 条，池子约 20 个候选。GT 不是"库里真正相关的有多少"，而是"这 20 个候选里有几个被判为相关"。

### 3.4 p07 被静默丢弃

`p07「傲娇双马尾美少女」`：20 个候选**全部标 false** → GT 为空 → `cmd_evaluate:498` 的 `if not gt: continue` 跳过它。

**35 条查询 → 34 条结果，少的那条没有任何提示。**

而 p07 恰恰是最有价值的一条 —— 它说明检索对这条查询完全跑偏。

> **已修（§9-A3）**：`_split_by_gt()` 分离空 GT 的查询，报告末尾单列"未参与统计的查询"，
> 并写入 `ground_truth_merged.json` 的 `dropped_queries` 字段。`--ablate` 同一处也改了。

## 4. NDCG 算错了 —— 已修（§9-A1）

### 4.1 `eval/metrics.py` 是一座孤岛

仓库里有**两份**指标实现：

| 文件 | 实现 | 消费者 |
|---|---|---|
| `eval/metrics.py` | `recall_at_k` / `precision_at_k` / `mrr` / **`ndcg_at_k`** | **0 处** |
| `eval/rag_eval.py:421-467` | `_dcg` / `_ndcg` / `_compute_metrics` | RAG 评测全部 |

实测：`metrics.py` 的四个 IR 指标在整个仓库（除自身）**引用数为 0**。

**而 `metrics.py:115-119` 的 `ndcg_at_k` 写得完全正确**：

```python
ideal_order = sorted(ground_truth.values(), reverse=True)   # ✅ 全集 GT 降序
```

**正确的版本一直躺在隔壁文件里。`rag_eval.py` 自己重写了一份错的。**

### 4.2 bug ①：IDCG 参照系错误

```python
# rag_eval.py:425-429
def _ndcg(relevances):
    dcg = _dcg(relevances)
    ideal = sorted(relevances, reverse=True)   # ❌ 只排了「本次返回的 k 条」
    idcg = _dcg(ideal)
    return dcg / idcg if idcg > 0 else 1.0
```

解剖 p01（GT = 6 条，命中在第 3、4 位）：

```
DCG  = 1/log2(4) + 1/log2(5)                     = 0.9307

IDCG = _dcg(sorted([0,0,1,1,0], reverse=True))   = 1.6309   ← 只排了本次返回的 5 条
       报告值 = 0.9307 / 1.6309 = 0.571  ✓ 与报告对得上

IDCG = _dcg([1,1,1,1,1])                         = 2.9485   ← 应为全集 GT 的理想排序
       正确值 = 0.9307 / 2.9485 = 0.316

       → 虚高 1.81 倍
```

标准定义（Järvelin & Kekäläinen, 2002）：IDCG 是**集合中所有相关文档**的理想排序，不是检索结果自身的降序重排。

### 4.3 bug ②：检索彻底失败给满分

```python
return dcg / idcg if idcg > 0 else 1.0   # ← 全零时返回 1.0
```

```
_ndcg([0,0,0,0,0])  → DCG=0, IDCG=0 → 返回 1.0   ← 一条没召回 = 满分
_ndcg([])           → 同上        → 返回 1.0   ← 零结果 = 满分
```

现有数据里尚未触发（所有查询都有命中），但是活的地雷。

> **已修（§9-A1）**：私有 `_dcg`/`_ndcg` 已删除，改用 `eval.metrics.ndcg_at_k`
> （IDCG 取自全集 GT，零命中返回 0.0）。`rag_eval.py` 的 `import math` 随之成为死导入，一并删除。

## 5. Recall@K 的结构性天花板

| query | GT | 返回 | R@5 理论上限 | 报告值 |
|---|---|---|---|---|
| a03 京都动画 | 49 | 10 | 10/49 = 0.204 | 0.102 |
| a18 动画制作人 | 58 | 10 | 10/58 = 0.172 | 0.086 |
| a16 声优 | 55 | 10 | 10/55 = 0.182 | 0.091 |

auto 组 GT 中位数 **24**（最大 58），检索只返回 **10** 条。

> `Recall@5` 在 |GT| ≫ K 时不是"检索做得差"的证据 —— 分母里塞了 40+ 条永远进不了 top-5 的文档。

`rag_eval.py:27` 的注释写"auto（自动 GT，Recall 精确）"。**GT 确实是精确完整的 —— 而"完整"恰恰是让 Recall 不可解释的原因。**

## 6. 三种检索通道（背景知识）

库 = 一张表，1500 行。每行一部作品：`id / name / tags / year / score / 简介`。

检索 = 从 1500 行里找相关的。三条路：

| 通道 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **① 结构化** | SQL `WHERE tags @> 芳文社` | 准 | **死板** —— 只能字面匹配，用户说不出 tags 里的原词就查不到 |
| **② 名称** | trigram `name_search()` | 快 | 只认名字 |
| **③ 向量语义** | pgvector `hybrid_search()` | 灵活，能理解意思 | 模糊，可能召不相干的 |

**通道 ③ 需要"索引"**：把每部作品的简介喂给 embedding 模型 → 一串 1024 维数字；意思相近的作品数字串也相近。1500 × 1024 挨个比太慢，**索引是提前建好的加速结构**；pgvector 是 PostgreSQL 的插件，专干这个。

**生产环境三条通道融合使用**（`_run_retrieval`，顺序 keyword → name → vector）。

**而这正是评测的盲区**：
- auto 组用 SQL 造答案，又用 SQL 检索 → **只测了通道 ①，通道 ③ 完全没被覆盖**
- human 组三条都跑了，但答案池是系统自己出的（见 §3）

## 7. 修法

### A 类 · 明确的 bug，无设计争议 —— ✅ 2026-09-12 已实施，见 §9

| # | 改什么 | 位置 | 状态 |
|---|---|---|---|
| A1 | 删私有 `_dcg`/`_ndcg`，改用 `eval.metrics.ndcg_at_k` | `rag_eval.py` | ✅ |
| A2 | GT SQL 加 `nsfw = false`，与检索对齐 | `rag_eval.py` `build_auto_gt()` | ✅ |
| A3 | GT 为空不再静默 `continue`，报告丢弃条数与原因 | `rag_eval.py` `_split_by_gt()` | ✅ |
| A4 | `--build` 防呆：已有标注时拒绝重建池化模板 | `rag_eval.py` `cmd_build()` | ✅ 追加 |

> 注：`metrics.ndcg_at_k` 接受 `dict[str, int]`（分级相关度），当前是二值 —— 传 `{id: 1 for id in gt}` 即可。
> 改完 A1 后，`_compute_metrics` 里 `NDCG@K` 的语义变为"前 K 位命中数"的折损加权，与 `Precision@K` 单调相关。信息量仍有限，但至少正确。

#### A4 的由来（原计划外）

A2 要求重跑 `--build`，但 `cmd_build()` 的 Phase 2 会**重建池化模板并把 `relevant` 全部重置为 null**
—— 即销毁已有的 183 条人工标注。这是执行 A2 时才会暴露的数据安全问题，已加防呆：
检测到已有标注则跳过重建并提示"确实要重建请先删除该文件"。

### B 类 · 报告形状（有设计取舍，建议已给出）

**B1 — auto 组改「按通道分层报告」而不是删除。**（建议）

不要问"融合后 P@5 多少"，改问"**每条通道各自找到几部**"：

```
a01 芳文社  (GT=31)
  keyword 通道 : 10/10 命中   P@5=1.0    ← 永远为真，降级为回归监控
  name    通道 :  0/10 命中               ← 有信息量
  vector  通道 :  ?/10 命中               ← 有信息量 ★ 这才是想知道的
  融合后       : P@5=1.0（全部来自 keyword，vector 贡献 0）
```

**为什么建议改造而非删除**：SQL 造标准答案本身是对的（客观、完整、零成本），错的只是"用同一个条件去检索"。分层后，这 18 条从废数据变成**语义通道的探针** —— 它回答"向量模型认不认得「芳文社」「ufotable」这类专有名词"。大概率答得很差，**但差本身是有价值的架构结论**（说明这类查询必须靠 keyword 兜底）。

**B2 — `Recall@K` 在 |GT| > K 时标注不可解释**，或对 auto 组改用 `Precision@K` 作主指标。

### C 类 · 需要重新标注（人工成本，待决）

**C1 — human 组候选池重造**：用**多个不同配置的并集**替代单一配置。

现在 `build_pooled_template` 只用 `hybrid_search(limit=15) × 2 路`。仓库里已有现成的 5 个消融配置（`ABLATION_CONFIGS`）+ `name_search` + `_run_keyword_search` —— 全部跑一遍取并集，能把"任一通道能找到的"都纳入池子。

**代价**：候选数会从 ~20 涨到 ~40–50，需要重新人工标注。**不做则把池化偏差写进报告头，human 组数字只作定性使用。**

### D 类 · 需要拍板的决定

1. **auto 组 18 条**：改造（分层报告，建议）还是删除？
2. **human 组候选池**：现在重造（要重新标注）还是先接受偏差、只作定性？
3. **`Recall@K` 的去留**：保留但标注局限，还是换 `Precision@K` 当主指标？
